# Wegent 知识库成果工作台 MVP 代码可行性与实施拆分

| 文档信息 | 内容 |
| --- | --- |
| 状态 | 待开发 |
| 创建日期 | 2026-07-26 |
| 关联技术设计 | `260726_1205_Wegent知识库成果工作台MVP技术设计.md` |
| MVP 范围 | 简报、思维导图 |

## 1. 结论

当前代码已经具备实现 MVP 的主要能力，可以直接进入开发，不需要先建设新的任务引擎。

```text
Artifact API
  → RedisArtifactRepository
  → 预制 wegent-notebook 智能体
  → prepare_execution_session
  → selected_documents 上下文
  → build_execution_request
  → ExecutionDispatcher
  → Assistant Subtask 结果
  → Artifact 读时对账
```

实现时遵循以下边界：

1. 不从后端通过 HTTP 调用自己的 `/v1/responses` 接口。
2. 不复制 WebSocket `chat:send` 的任务创建逻辑。
3. 直接组合现有会话创建、上下文注入、请求构建和执行调度服务。
4. Redis 使用单知识库单 Hash，不使用事务、ZSET 或 Cluster Hash Tag。
5. 一期只实现简报和思维导图，不实现 PPT。

## 3. 对技术设计的代码级修正

### 3.1 必须保存 Assistant Subtask ID

Artifact 除 `task_id` 外，还应保存：

```text
assistant_subtask_id
```

原因：

- Task 是会话容器，Assistant Subtask 才是单次生成的状态和输出事实源。
- 最终文本保存在 `Subtask.result.value`。
- 重试会产生新的 Assistant Subtask，只保存 `task_id` 无法稳定定位本次生成。
- 通过已知 Subtask ID 查询比扫描 Task 下的“最新助手消息”更明确。

读时对账应以 `assistant_subtask_id` 为主，Task 状态只用于辅助诊断。

### 3.2 后台 Task 隐藏存在现有缺口

`create_new_task()` 当前固定写入 `metadata.labels.type=online`。即使随后改成
`background`，个人任务列表的 `_filter_personal_tasks()` 仍会把非 subscription、
非 code 的 Task 当成 online 返回。

MVP 需要做最小修正：

1. 创建 Artifact Task 后写入：

```text
type=background
taskType=knowledge
source=knowledge_artifact
artifactId=<artifact_id>
```

2. 修改个人任务列表过滤逻辑，明确排除 `type=background`。
3. 增加回归测试，确保后台 Artifact Task 不出现在普通任务历史。

一期接受后台 Task 仍参与底层总数查询的局限，不为此新增 Task 状态或修改表结构。

### 3.3 不直接复用 RedisCache

`backend/app/core/cache.py` 中的 `RedisCache`：

- 只提供普通 GET/SET 缓存语义，没有 Artifact 所需的 Hash 接口。
- 读取或写入失败时返回 `None`、`False` 或空结果。
- 默认支持 TTL。

Artifact 永久存储不能静默降级，因此新增独立 `RedisArtifactRepository`，直接封装
`HSET`、`HGET`、`HGETALL`、`HDEL` 和 `DEL`，Redis 异常必须向 Service 抛出并映射
为 503。

### 3.4 前端 Tab 需要适配现有权限 Tab

`DocumentPanel` 当前已有“文档/权限”Tab，并非只有文档列表。最小改造为始终使用
统一 Tab：

```text
文档 | 成果 | 权限（有权限时展示）
```

没有权限管理能力的用户展示：

```text
文档 | 成果
```

不增加第三栏，也不在 DocumentPanel 外再嵌套一层 Tab。

## 4. 后端目标流程

### 4.1 创建 Artifact

```text
1. 校验知识库访问与文档管理权限
2. 校验 document_ids 均属于当前知识库且 index_status=success
3. document_ids 为空时获取当前知识库全部已索引文档
4. 生成 artifact_id
5. HSET 写入 queued Artifact
6. 解析 DEFAULT_TEAM_KNOWLEDGE，获取 wegent-notebook
7. prepare_execution_session() 创建 Task/Subtask
8. 写入 background、source、artifactId 等 Task labels
9. 为 User Subtask 创建 selected_documents 上下文
10. build_execution_request() 构建执行请求
11. HSET 回写 task_id、assistant_subtask_id 和 running
12. 后台调用 ExecutionDispatcher.dispatch()
13. 返回 Artifact
```

后台执行必须使用会持续消费事件的协程：

```text
SSEResultEmitter
  ├── ExecutionDispatcher.dispatch()
  └── emitter.collect()
```

不能只创建 `SSEResultEmitter` 而不消费，否则生成期间的事件会持续堆积在内存队列。

### 4.2 读时对账

列表或详情查询遇到 queued/running Artifact 时：

1. 按 `assistant_subtask_id` 批量查询 Assistant Subtask。
2. 将 PENDING、RUNNING、COMPLETED、FAILED、CANCELLED 映射为 Artifact 状态。
3. COMPLETED 时从 `result.value` 读取最终文本。
4. briefing 直接保存 Markdown。
5. mind_map 提取唯一 Mermaid 代码块；缺失或存在多个代码块时标记失败。
6. 将最新状态和结果 HSET 回 Redis。

一期不增加 TaskCompletedEvent 监听、完成回调或定时任务。

### 4.3 重试

重试保持 `artifact_id` 不变：

1. 只允许 failed Artifact 重试。
2. 复用 `source_document_ids` 和 `generation_config`。
3. 创建新的 Task 和 Assistant Subtask。
4. 替换 `task_id`、`assistant_subtask_id`。
5. 清空旧结果和错误，状态改为 running。

## 5. API 契约

### 5.1 创建

```http
POST /api/knowledge-bases/{knowledge_base_id}/artifacts
```

```json
{
  "artifact_type": "briefing",
  "title": "产品资料简报",
  "document_ids": [101, 102],
  "instruction": "突出核心结论和下一步行动"
}
```

`artifact_type` 只接受 `briefing`、`mind_map`。服务端不接受 Team、Bot、Skill、
Prompt 模板或模型 ID。

### 5.2 列表与详情

```http
GET /api/knowledge-bases/{knowledge_base_id}/artifacts
GET /api/knowledge-bases/{knowledge_base_id}/artifacts/{artifact_id}
```

列表读取 Redis Hash 全量数据，在应用层按 `created_at` 倒序排序并返回最近 50 条。

### 5.3 管理

```http
PATCH  /api/knowledge-bases/{knowledge_base_id}/artifacts/{artifact_id}
POST   /api/knowledge-bases/{knowledge_base_id}/artifacts/{artifact_id}/retry
DELETE /api/knowledge-bases/{knowledge_base_id}/artifacts/{artifact_id}
```

PATCH 一期只修改标题。删除只执行 `HDEL`，不删除 Task。

### 5.4 响应核心字段

```json
{
  "artifact_id": "uuid",
  "knowledge_base_id": 1,
  "artifact_type": "briefing",
  "title": "产品资料简报",
  "status": "running",
  "task_id": 1001,
  "assistant_subtask_id": 1003,
  "content": null,
  "source_document_ids": [101, 102],
  "generation_config": {
    "instruction": "突出核心结论和下一步行动"
  },
  "error_message": null,
  "created_at": "2026-07-26T12:42:00+08:00",
  "updated_at": "2026-07-26T12:42:01+08:00",
  "completed_at": null
}
```

## 8. 必测场景

### 后端

- 无知识库访问权限返回 404。
- 有访问权限但无文档管理权限时，创建、重试、重命名和删除返回 403。
- 跨知识库 document_ids 返回 422。
- 未索引完成的文档返回 422。
- Redis 失败返回 503，不能返回空列表。
- Task 创建失败后 Artifact 为 failed。
- Assistant Subtask 完成后从 `result.value` 提取正文。
- Mermaid 输出不符合唯一代码块约定时 Artifact 为 failed。
- 重试替换 Task 和 Assistant Subtask ID。
- background Task 不出现在普通任务列表。
- Artifact Key 没有 TTL。

### 前端

- 文档、成果、权限 Tab 组合正确。
- 当前选中文档 ID 正确传入创建请求。
- queued/running 时轮询，终态停止。
- 简报和思维导图进入正确 Viewer。
- 只读用户可以查看成果，但看不到管理操作。
- 切换知识库后不显示上一个知识库的成果。
- 简报保存弹窗默认当前知识库，且允许修改标题与正文。

## 9. 当前非阻塞局限

1. `HGETALL` 会读取单知识库全部 Artifact，数据量增长后再增加索引分页。
2. Artifact JSON 为最后写入生效，并发重命名与状态回写存在低概率覆盖风险。
3. background Task 仍可能进入底层任务总数统计，一期只保证不在普通任务列表展示。
4. 读时对账意味着没有用户查询时，Redis 状态不会立即进入终态。

这些局限不阻塞 MVP，不建议在第一版引入 Redis 事务、分布式事务、回调系统或定时修复任务。
