# Wegent 知识库成果工作台 MVP 产品设计

| 文档信息 | 内容 |
| --- | --- |
| 状态 | 讨论稿 |
| 创建日期 | 2026-07-26 |
| 版本 | 0.2 |
| 产品范围 | 知识库笔记本视图第一版 MVP |
| UI 名称 | 成果 |
| 内部对象名 | Artifact |

## 1. Executive Summary / 执行摘要

### 一句话定义

在知识库笔记本视图中增加“成果工作台”，让用户基于当前知识库文档一键生成演示文稿、思维导图和简报报告，并持续查看、预览和下载生成结果。

### 核心结论

第一版不照搬 NotebookLM 的固定三栏布局，而是在 Wegent 现有“对话区 + 文档面板”两栏结构上，将右侧文档面板升级为包含“来源”和“成果”两个 Tab 的知识工作台。

产品必须同时表达三个逻辑对象，但不要求三个对象同时并排：

```text
来源（看什么） → 对话（理解与加工） → 成果（交付什么）
```

MVP 只验证一条核心价值链：

```text
选择来源 → 发起生成 → 后台执行 → 成果持续可见 → 预览、下载或复用
```

### 快速事实

- 主要用户：进入知识库进行问答、研究、总结和内容生产的知识工作者。
- 核心问题：当前笔记本视图能问答、能选文档，但高价值输出隐藏在对话或工具执行中，缺少可感知、可回访的成果。
- 核心指标：每周成功生成且被打开、下载或保存的成果数。
- 产品目标：增强知识库的产品表现力，同时形成从知识到工作成果的完整闭环。
- MVP 成果类型：演示文稿、思维导图、简报报告。

## 2. Problem Statement / 背景与问题

### 2.1 当前状态

Wegent 当前知识库笔记本视图的主体是：

- 左侧对话区：围绕当前知识库发起任务对话。
- 右侧文档面板：浏览、选择、上传和管理知识库文档。
- 外层知识库导航：进入笔记本视图后自动收起，为对话释放空间。

这一结构已经具备“来源 + 对话”的基础，但缺少独立的成果承载区：

- 用户不知道知识库除了问答还能生成什么。
- PPT、报告等生成结果容易埋在聊天消息或工具调用记录中。
- 用户离开当前任务后，难以重新找到生成结果。
- 不同类型结果缺少对应的预览与使用方式。
- 知识库页面没有形成直观的“输入知识、产出成果”产品叙事。

### 2.2 用户问题

用户使用知识库的目的通常不是阅读文档本身，而是完成工作，例如：

- 将多份资料整理成汇报 PPT。
- 快速理解复杂主题的结构和关系。
- 形成可发送、可复用的简报或总结。

当前产品要求用户通过对话自行描述这些需求，结果也只存在于对话中，使用门槛和发现成本较高。

### 2.3 业务问题

- 笔记本视图与普通知识库问答的差异不够明显。
- 知识库的能力价值依赖用户是否会写 Prompt，缺乏显性功能入口。
- 产品缺少直观、适合演示的生成过程和成果展示。
- 已有任务、技能和文件生成能力没有被包装成统一的用户体验。

### 2.4 为什么现在做

本阶段优先目标是增强知识库的产品表现力和用户激活，而不是先建设完整的可信研究、笔记编辑或协作发布系统。因此第一版应优先把已有生成能力产品化，形成最短、最直观的价值闭环。

## 3. 第一性原理与产品边界

### 3.1 最小用户价值

Studio 类功能成立的必要条件不是存在若干生成按钮，而是用户能够：

1. 明确 AI 使用了哪些知识。
2. 用低成本发起一种明确成果的生成。
3. 在生成时间较长时仍能看到任务状态。
4. 生成完成后获得适合该类型的预览。
5. 离开当前对话后仍能找回成果。
6. 将成果用于下一步工作。

缺少其中任意一项，功能都会退化成“预置 Prompt”或“聊天附件”，无法形成独立产品价值。

### 3.2 三个核心对象

| 对象 | 产品含义 | 数据来源 | 生命周期 |
| --- | --- | --- | --- |
| 来源 Source | AI 本次应该读取的知识范围 | 知识库文档 | 随知识库持续存在 |
| 对话 Task | 用户与智能体的探索、澄清和加工过程 | 任务消息 | 随任务持续存在 |
| 成果 Artifact | 可独立查看和使用的工作产出 | 一次生成任务 | 随知识库持续存在 |

### 3.3 Source of Truth

- 知识库文档是来源内容的唯一事实源。
- Task 是对话过程的唯一事实源。
- Artifact 是生成成果及其状态的唯一事实源。
- 附件只负责承载 PPTX、PDF 等二进制文件，不代表完整的 Artifact 生命周期。
- Artifact 不自动成为知识库文档；只有用户明确执行“保存为知识库文档”后才进入知识库。

### 3.4 为什么不固定三栏

NotebookLM 的三栏适合完全受 Notebook 约束的产品。Wegent 还存在外层知识库导航、任务对话和未来跨知识库的智能体工作流。如果同时展示导航、来源、对话和成果，会压缩主要工作区，并增加界面层级。

因此 MVP 采用：

- 三个逻辑区域：来源、对话、成果。
- 两个同时显示的物理区域：对话区、知识工作台。
- 右侧知识工作台通过 Tab 在“来源”和“成果”之间切换。

这既保留清晰的产品叙事，也能直接复用现有笔记本视图结构。

## 4. Goals & Objectives / 产品目标与非目标

### 4.1 产品目标

1. 用户进入非空知识库后，可以立即看到可生成的成果类型。
2. 用户无需编写完整 Prompt，即可基于明确来源生成成果。
3. 生成任务可以异步运行，离开当前对话后仍可查看状态和结果。
4. 不同成果拥有适合自身类型的预览和消费方式。
5. 产品在演示时能够直观体现“知识转化为工作成果”的价值。

### 4.2 Out of Scope / 非目标

第一版不解决以下问题：

- 精确到段落或句子的可信引用闭环。
- 手写笔记和富文本笔记编辑。
- 未发布草稿。
- 私人笔记与共享知识分离。
- 独立的 Artifact 协作权限。
- 审核、发布和审批流程。
- 复杂版本历史。
- 完整 PPT 在线编辑器。
- 音频、视频、信息图、闪卡和测验。
- 任意 Artifact 类型或用户自定义生成器。
- 自动判断哪些对话值得沉淀。
- 自动将生成结果写入知识库。
- 普通任务页面中的全局 Studio。

### 4.3 In Scope / MVP 范围

第一版范围严格限定为：

- 知识库笔记本视图中的成果工作台。
- 演示文稿、思维导图和简报报告三种成果。
- 知识库级成果列表、异步状态和类型化预览。
- 简报报告由用户确认后保存为知识库文档。

## 5. User Personas / 目标用户与核心场景

### 5.1 主要用户

**知识工作者**

- 在知识库中查找、理解和整理资料。
- 能描述业务目标，但不希望学习复杂 Prompt。
- 希望快速得到可以阅读、汇报或继续加工的成果。
- 对生成过程的可见性和结果可找回性有明确需求。

### 5.2 核心场景

#### 场景一：生成汇报材料

用户选择若干产品资料，生成一份用于内部汇报的 PPT，预览后下载 PPTX。

#### 场景二：理解知识结构

用户基于整个知识库生成思维导图，直接查看知识结构。

#### 场景三：形成简报

用户选择多份资料生成简报，在页面内阅读，并将结果保存为知识库文档供后续使用。

## 6. Design & UX Requirements / 信息架构与页面设计

### 6.1 桌面端整体布局

```text
┌──────────────────────────────────────────────────────────────┐
│ 知识库名称       来源：全部文档 / 已选 6 个       新建对话   │
├──────────────────────────────────┬───────────────────────────┤
│                                  │  来源  |  成果             │
│                                  ├───────────────────────────┤
│                                  │  [演示文稿] [思维导图]     │
│             对话区               │  [简报报告]                │
│                                  ├───────────────────────────┤
│                                  │  最近成果                  │
│                                  │  ● 产品分析报告            │
│                                  │  ◌ 市场汇报 PPT 生成中     │
└──────────────────────────────────┴───────────────────────────┘
```

### 6.2 布局规则

- 对话区默认占可用宽度的 60%～65%。
- 知识工作台默认占 35%～40%，保持现有可调整宽度和折叠能力。
- 工作台顶部固定显示“来源”和“成果”Tab。
- 知识库有文档时，首次进入默认打开“成果”Tab，突出生成能力。
- 知识库没有文档时，默认打开“来源”Tab，并显示上传引导。
- 用户切换 Tab 后，在当前知识库会话期间保留选择。
- 对话区顶部显示当前来源范围，点击后切换至“来源”Tab。
- 打开成果后使用大尺寸预览层或全屏预览，不在狭窄右栏内展示完整内容。

### 6.3 移动端布局

移动端采用页面级 Tab：

```text
对话 | 来源 | 成果
```

- 三个区域不同时显示。
- 生成状态在“成果”Tab 上显示数量或状态提示。
- 打开成果进入独立全屏页面。

### 6.4 成果工作台结构

“成果”Tab 分为上下两部分：

#### 生成入口

固定展示三个真实可用的生成卡片：

| 卡片 | 价值说明 | 主视觉 |
| --- | --- | --- |
| 演示文稿 | 将资料转成可汇报的幻灯片 | PPT 页面缩略图 |
| 思维导图 | 展示主题、层级和关系 | 节点关系图 |
| 简报报告 | 提炼重点、结论和行动建议 | 文档摘要 |

禁止展示尚未实现的置灰类型，避免形成“功能很多但不可用”的感知。

#### 最近成果

按创建时间倒序展示当前知识库的成果：

- 标题。
- 类型图标。
- 创建人。
- 创建时间。
- 生成状态。
- 失败原因摘要。
- 未查看提示。

## 7. 核心交互流程

### 7.1 来源范围规则

生成时使用的来源范围按以下优先级确定：

1. 当前已选择一个或多个文档：使用所选文档。
2. 当前没有选择文档：使用当前知识库的全部可用文档。
3. 当前知识库没有可用文档：禁止生成，并引导用户上传文档。

其他规则：

- 生成确认界面必须明确显示来源范围。
- 用户可以从确认界面进入“来源”Tab 修改选择。
- 发起生成后记录文档 ID 快照，后续切换文档选择不影响已发起任务。
- MVP 不默认使用当前聊天记录作为成果来源。
- 索引失败、处理中或用户无权访问的文档不进入生成范围。

### 7.2 发起生成

1. 用户点击成果类型卡片。
2. 系统打开轻量生成确认框。
3. 确认框展示成果类型、来源范围和可选的补充要求。
4. 用户点击“开始生成”。
5. 系统创建 Artifact，并立即在最近成果列表顶部显示“等待中”。
6. 后台执行生成任务，状态更新为“生成中”。
7. 用户可以继续对话、切换 Tab 或离开当前任务。
8. 任务完成后更新为“已完成”，并显示未查看提示。
9. 用户点击成果进入对应预览。

### 7.3 生成确认框

所有类型共有以下字段：

| 字段 | 是否必填 | 规则 |
| --- | --- | --- |
| 成果类型 | 是 | 由入口确定，不允许在确认框内切换 |
| 来源范围 | 是 | 显示全部文档或已选文档数量，可跳转修改 |
| 补充要求 | 否 | 自然语言输入，限制合理长度 |

MVP 不提供模型、技能、模板、主题色等高级配置。生成器使用服务端预设的稳定配置。

### 7.4 状态模型

| 状态 | 用户展示 | 可执行操作 |
| --- | --- | --- |
| queued | 等待生成 | 查看来源 |
| running | 正在生成 | 查看来源 |
| succeeded | 已完成 | 打开、下载、重命名、删除 |
| failed | 生成失败 | 查看原因、重试、删除 |

MVP 不提供取消生成。相同来源和类型允许生成多个成果。

### 7.5 成果预览

#### 演示文稿

- 直接复用现有 Office 预览能力，不新建 PPT 专用预览器。
- 预览交互和格式支持范围以现有 Office 预览能力为准。
- 支持下载 PPTX。
- 不支持在线修改单页内容。

#### 思维导图

- 展示可视化节点。
- 第一版只要求用户能够查看完整导图。
- 优先使用最简单的现有渲染方案，不建设专用编辑器。
- 如通用 `content` 字段可以直接保存可渲染文本，则复用该字段；不建设独立文件或结构化存储方案。
- MVP 不支持直接编辑节点。
- MVP 不支持导出。

#### 简报报告

- 使用 Markdown 阅读视图。
- 支持复制全文。
- 支持保存为知识库文档。
- 保存前允许修改文档标题和正文。

### 7.6 成果管理

MVP 支持：

- 打开成果。
- 重命名成果。
- 删除成果。
- 对失败成果重试。
- 下载有文件载荷的成果。
- 查看生成时的来源范围。

MVP 不支持：

- 文件夹分类。
- 收藏和标签。
- 版本对比。
- 多人评论。
- 审核和发布。
- 对成功成果进行局部指令修改。

## 8. User Stories & Requirements / 用户故事与验收标准

### US-01：发现生成能力

**用户故事**

作为进入知识库的用户，我希望直接看到可以生成的成果类型，从而无需先学习如何编写 Prompt。

**验收标准**

- [ ] 非空知识库首次进入笔记本视图时，右侧工作台默认显示“成果”Tab。
- [ ] 页面固定展示演示文稿、思维导图、简报报告三个可用卡片。
- [ ] 不展示未实现的成果类型。
- [ ] 知识库无可用文档时，默认打开“来源”Tab 并展示上传引导。

### US-02：控制生成来源

**用户故事**

作为知识库用户，我希望明确选择本次生成使用的文档，从而控制成果范围。

**验收标准**

- [ ] 用户可以在“来源”Tab 选择或取消选择文档。
- [ ] 对话区顶部和生成确认框展示相同的来源范围。
- [ ] 未选择文档时，界面明确显示“全部可用文档”，而不是显示空选择。
- [ ] 发起生成后保存来源文档 ID 快照。
- [ ] 没有可用文档时不能发起生成。

### US-03：异步生成成果

**用户故事**

作为用户，我希望发起生成后继续其他操作，从而不必停留在当前页面等待。

**验收标准**

- [ ] 点击“开始生成”后立即在成果列表创建记录。
- [ ] 成果状态至少包含等待中、生成中、已完成和失败。
- [ ] 用户切换对话或离开当前页面后，生成任务继续执行。
- [ ] 用户重新进入知识库后可以看到最新状态。
- [ ] 生成失败时显示可理解的原因和重试入口，不暴露技术堆栈。

### US-04：查看不同类型成果

**用户故事**

作为用户，我希望直接预览生成结果，从而在下载或复用前判断其是否可用。

**验收标准**

- [ ] 演示文稿可以通过现有 Office 预览能力打开和查看。
- [ ] 思维导图可以完整展示，用户无需具备编辑或导出能力。
- [ ] 简报报告支持 Markdown 阅读和复制。
- [ ] 预览失败时仍保留下载或重试能力。
- [ ] 用户打开成果后清除未查看提示。

### US-05：回访和管理成果

**用户故事**

作为用户，我希望离开当前对话后仍能找到生成结果，从而持续使用知识库产出。

**验收标准**

- [ ] 成果列表属于知识库，不依赖当前选中的 Task。
- [ ] 同一知识库支持多个同类型成果。
- [ ] 成果按创建时间倒序显示。
- [ ] 有管理权限的用户可以重命名和删除成果。
- [ ] 删除前必须二次确认；删除完成后列表立即更新。

### US-06：将简报沉淀为知识

**用户故事**

作为知识库管理者，我希望将有价值的简报保存为知识库文档，从而供后续检索和对话使用。

**验收标准**

- [ ] 已完成的简报报告显示“保存为知识库文档”操作。
- [ ] 保存前可以修改文档标题和正文。
- [ ] MVP 固定保存到当前知识库根目录，不提供目录选择。
- [ ] 保存成功后生成普通文本类知识库文档并进入现有索引流程。
- [ ] 保存失败不影响原 Artifact，用户可以重试。
- [ ] PPT 和思维导图第一版不自动转成知识库文档。

## 9. 功能需求

| 编号 | 功能 | MVP 优先级 |
| --- | --- | --- |
| FR-001 | 将右侧文档面板升级为“来源 / 成果”工作台 | 必须 |
| FR-002 | 展示演示文稿、思维导图、简报报告生成卡片 | 必须 |
| FR-003 | 复用当前文档选择并明确显示来源范围 | 必须 |
| FR-004 | 创建并持久化知识库级 Artifact | 必须 |
| FR-005 | 支持等待中、生成中、已完成、失败状态 | 必须 |
| FR-006 | 支持后台生成和页面重新进入后的状态恢复 | 必须 |
| FR-007 | 提供三种类型对应的预览能力 | 必须 |
| FR-008 | 支持 PPTX 下载和报告复制 | 必须 |
| FR-009 | 支持重命名、删除和失败重试 | 必须 |
| FR-010 | 支持简报保存为知识库文本文件 | 必须 |
| FR-011 | 展示创建人、创建时间和来源范围 | 必须 |
| FR-012 | 成果完成后显示未查看状态提示 | 必须 |

## 10. 权限规则

MVP 不建立新的权限体系，完全继承知识库现有权限。

| 操作 | 权限规则 |
| --- | --- |
| 查看成果列表和预览成果 | 能访问当前知识库 |
| 下载成果 | 能访问当前知识库 |
| 发起生成 | 能管理当前知识库文档 |
| 重试生成 | 能管理当前知识库文档 |
| 重命名、删除成果 | 能管理当前知识库文档 |
| 保存简报为知识库文档 | 能管理当前知识库文档 |

设计原因：

- Artifact 是知识库级共享对象，生成会改变共享成果列表。
- 如果允许所有只读用户生成，但又不增加私人区或独立权限，会造成共享列表污染。
- MVP 复用现有文档管理权限，避免新增角色和协作模型。

## 11. 最小数据模型

Artifact 需要成为知识库级一等对象，最小字段如下：

| 字段 | 说明 |
| --- | --- |
| id | 成果 ID |
| knowledge_base_id | 所属知识库 |
| type | presentation、mind_map、briefing |
| title | 成果标题 |
| status | queued、running、succeeded、failed |
| payload_type | content 或 attachment |
| content | 报告正文或脑图结构化内容 |
| attachment_id | PPTX、PDF 等文件附件 |
| source_document_ids | 发起生成时的来源文档 ID 快照 |
| generation_config | 补充要求及服务端生成配置快照 |
| error | 可展示的失败信息 |
| created_by | 创建人 |
| created_at | 创建时间 |
| updated_at | 更新时间 |

约束：

- 一个 Artifact 只属于一个知识库。
- 一个 Artifact 可以引用多个来源文档。
- Artifact 不绑定当前 Task，不因用户切换或删除当前对话而丢失。
- 权限通过所属知识库计算，不保存独立成员关系。
- 删除 Artifact 时只复用现有删除和附件生命周期能力。
- MVP 不新增附件引用检查、物理回收或垃圾清理代码；现有能力没有覆盖时暂不主动删除底层附件。

## 12. Technical Considerations / 技术与系统约束

### 12.1 高层流程

```text
前端创建 Artifact
    ↓
服务端校验知识库权限和来源文档
    ↓
按 Artifact 类型选择受控生成器
    ↓
后台执行生成任务
    ↓
保存结构化内容或上传生成文件
    ↓
更新 Artifact 状态和载荷
    ↓
前端轮询或接收状态更新并展示结果
```

MVP 统一采用现有轮询方式更新状态，不新增实时推送通道。

### 12.2 生成器边界

- 前端只提交成果类型、来源范围和补充要求。
- 服务端维护“成果类型 → 生成器”的固定映射。
- 用户不能指定任意技能、工具名、模型或执行命令。
- 三种成果必须共享统一的创建、状态、错误和查询契约。
- 类型差异只存在于生成配置、结果载荷和预览器。

### 12.3 最小接口能力

MVP 至少需要以下能力，具体 URL 由技术设计确定：

- 创建 Artifact。
- 查询知识库 Artifact 列表。
- 查询单个 Artifact 详情。
- 更新 Artifact 标题。
- 删除 Artifact。
- 重试失败 Artifact。
- 获取或刷新 Artifact 状态。

### 12.4 非功能要求

| 编号 | 类别 | 要求 |
| --- | --- | --- |
| NFR-001 | 状态一致性 | 页面刷新或重新进入后，成果状态与服务端一致 |
| NFR-002 | 可靠性 | 单个生成任务失败不得影响对话和其他成果 |
| NFR-003 | 安全 | 所有查询、生成、下载和删除操作均执行服务端知识库权限校验 |
| NFR-004 | 可理解性 | 错误信息不得展示堆栈、内部路径或敏感配置 |
| NFR-005 | 响应式 | 桌面端两栏，移动端页面级 Tab |
| NFR-006 | 可访问性 | 所有交互元素可键盘访问，状态不只依赖颜色表达 |
| NFR-007 | 国际化 | 新增文案进入现有中英文国际化体系 |

## 13. Success Metrics / 成功指标

MVP 使用 HEART 中的 Adoption、Engagement 和 Task Success 维度，重点判断用户是否发现、完成并消费成果。

### 13.1 北极星指标

**每周有效成果数**

定义：一周内生成成功，并且至少发生一次打开、下载、复制或保存为知识库文档的 Artifact 数量。

该指标同时约束“成功生成”和“被实际使用”，避免只统计按钮点击或任务创建数。

### 13.2 灰度目标

以下为灰度期初始目标，发布后根据真实基线校准：

| 指标 | 定义 | 灰度 4 周目标 |
| --- | --- | --- |
| 功能采用率 | 使用成果工作台的用户 / 笔记本视图周活用户 | ≥ 15% |
| 生成成功率 | succeeded Artifact / 已进入执行的 Artifact | ≥ 90% |
| 成果消费率 | 被打开、下载、复制或保存的成功成果 / 成功成果 | ≥ 60% |
| 失败重试成功率 | 重试后成功的成果 / 被重试的失败成果 | ≥ 70% |
| 权限异常率 | 因前后端权限不一致导致的失败 / 创建请求 | < 0.5% |

### 13.3 关键埋点

| 事件 | 触发时机 |
| --- | --- |
| `kb_artifact_tab_viewed` | 用户打开“成果”Tab |
| `kb_artifact_create_started` | 用户确认开始生成 |
| `kb_artifact_create_succeeded` | 成果生成成功 |
| `kb_artifact_create_failed` | 成果生成失败 |
| `kb_artifact_opened` | 用户打开成果 |
| `kb_artifact_downloaded` | 用户下载成果 |
| `kb_artifact_copied` | 用户复制报告 |
| `kb_artifact_saved_to_kb` | 用户将简报保存为知识库文档 |
| `kb_artifact_deleted` | 用户删除成果 |

所有事件至少包含：

- knowledge_base_id
- artifact_id
- artifact_type
- source_document_count
- task_id（如创建时存在，仅用于分析，不作为归属）
- result_status

## 14. Risks & Mitigation / 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 三栏照搬导致界面拥挤 | 对话和成果预览空间不足 | 使用对话区 + 工作台两栏，来源和成果通过 Tab 切换 |
| 只有生成按钮，没有成果承载 | 功能退化成预置 Prompt | Artifact 必须持久化并出现在知识库级列表 |
| PPT 质量不稳定 | 强表现力入口反而损害信任 | 使用固定生成模板和默认结构，灰度期收集失败与下载数据 |
| 生成耗时长 | 用户误以为卡死 | 创建后立即显示状态，支持离开页面和重新进入 |
| 来源范围不明确 | 用户无法判断结果为何偏题 | 在对话顶部、确认框和成果详情中持续展示来源范围 |
| 共享知识库成果被滥用 | 列表被大量低价值结果污染 | 创建和管理复用知识库文档管理权限 |
| Artifact 自动入库造成知识污染 | 检索质量下降、重复内容增加 | 只有简报支持用户明确确认后保存为知识库文档 |
| 三种生成链路各自实现 | 状态和错误体验不一致 | 共用 Artifact 状态机和创建、查询、重试契约 |

## 15. Dependencies & Assumptions / 依赖与假设

### 15.1 依赖

- 现有知识库文档选择能力。
- 现有知识库文档访问和管理权限判断。
- 可在后台执行长耗时生成任务的任务基础设施。
- 现有附件上传、下载和 Office 文件预览能力。
- 演示文稿、Markdown 和最简思维导图生成与渲染能力。
- 简报保存为文本知识库文档及现有索引流程。

### 15.2 假设

- MVP 只在知识库笔记本视图中提供成果工作台。
- 三种生成器在上线前能够达到可查看的最低质量，演示文稿额外支持下载 PPTX。
- 知识库文档数量较多时，生成器可以通过现有知识检索或材料注入机制获得内容。
- 第一版复用现有轮询方式刷新生成状态，不建设新的实时推送通道。
- 第一版不新增并发上限、超时或资源配额等业务限制，沿用现有任务基础设施的默认行为。
- 不为历史聊天附件自动补建 Artifact。

## 17. MVP Definition of Done

只有同时满足以下条件，第一版才算完成：

- [ ] 笔记本视图形成“对话 + 来源/成果工作台”两栏体验。
- [ ] 三个生成卡片均对应真实、可完成的生成能力。
- [ ] 用户在发起前能明确知道使用了哪些来源。
- [ ] 生成任务支持跨页面持续执行和状态恢复。
- [ ] 成果属于知识库，不依赖当前 Task。
- [ ] PPT 复用现有 Office 预览，思维导图可以查看，简报可以阅读。
- [ ] PPT 可以下载，报告可以复制并保存为知识库文档。
- [ ] 失败任务可以重试，错误信息对用户可理解。
- [ ] 所有操作通过服务端执行知识库权限校验。
- [ ] 桌面端和移动端均可完成核心流程。
- [ ] 关键行为已接入埋点，可以计算灰度指标。
- [ ] 未实现能力没有以置灰卡片或占位入口出现在页面上。
