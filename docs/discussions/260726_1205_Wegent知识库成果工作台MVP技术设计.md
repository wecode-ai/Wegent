## 1. 设计结论

MVP 采用“Redis 永久存储 Artifact + 复用现有智能体 Task 执行”的方案：

```text
Redis：Artifact 永久事实源，保存列表、来源快照、状态和结果
Task/Subtask：负责实际 AI 生成和工具执行
SubtaskContext：负责传递知识库及选中文档
```

不新增 MySQL 表和 Alembic 迁移。只新增 Redis Repository、Artifact
Service、API 和前端工作台，不新增第二套任务调度、文件存储、实时推送或附件回收机制。

一期只支持简报和思维导图，暂不实现 PPT 生成、Office 预览和下载。PPT 后续通过
预制 PPT 智能体接入，不改变 Artifact API 和业务模型。

核心原则：

1. Artifact 是知识库级业务对象，Task 只是其内部执行记录。
2. 所有生成任务复用现有 Task/Subtask 和统一 ExecutionDispatcher。
3. 前端只提交成果类型、文档范围和补充要求，不提交智能体、Skill 或工具名。
4. 服务端通过固定注册表选择预制智能体和输出解析方式。
5. 状态通过现有轮询刷新，不增加 WebSocket 事件。
6. 删除只处理 Artifact 记录，不删除关联 Task。
7. Redis Artifact Key 永久不设置 TTL，数据结构通过 `schema_version` 演进。
8. Artifact Redis 操作只允许通过 Repository 访问，避免存储细节进入业务层。

## 2. 现有能力复用

| 能力 | 现有实现 | MVP 用法 |
| --- | --- | --- |
| 笔记本两栏布局 | `KnowledgeDetailPanel.tsx` | 保留 ChatArea，扩展右侧 DocumentPanel |
| 文档选择 | `DocumentPanel`、`selectedDocumentIds` | 作为 Artifact 来源范围 |
| 选中文档注入 | `selected_documents.py`、`SubtaskContext` | 继续使用直接注入或 RAG 回退 |
| 知识库权限 | `KnowledgeService.can_manage_knowledge_base_documents()` | 控制创建、重试、重命名和删除 |
| 后台 AI 执行 | Task/Subtask、ExecutionDispatcher | 作为 Artifact 的执行引擎 |
| 后台任务隐藏 | Task `type=background` | 增加普通任务列表排除逻辑 |
| 状态轮询 | `useDocumentIndexPolling` 模式 | 新建轻量 Artifact 轮询 Hook |
| 思维导图 | `MermaidDiagram` / `EnhancedMarkdown` | 直接渲染 Mermaid 文本 |
| 保存知识库文档 | `WysiwygEditor`、附件上传与文档创建 API | 简报编辑后保存为 Markdown 文档 |

## 3. 总体架构

```text
成果工作台
    │
    ├── POST 创建 Artifact
    │      │
    │      ├── 校验知识库权限和来源文档
    │      ├── HSET 写入 queued Artifact
    │      ├── 创建隐藏 Task 并触发现有执行链路
    │      └── 回写 task_id、assistant_subtask_id 和 running 状态
    │
    └── GET Artifact 列表（活动状态时每 5 秒轮询）
           │
           ├── 批量读取关联 Assistant Subtask 状态
           ├── 终态时提取 Markdown 或 Mermaid
           ├── 回写 Redis Artifact
           └── 返回成果列表
```

MVP 不增加任务完成回调。Artifact 查询接口负责对仍处于活动状态的记录进行“读时对账”，因此用户刷新页面或重新进入知识库时仍能得到最终状态。

## 4. Redis 存储模型

### 4.1 单 Key 结构

```text
key   = knowledge-artifacts:<knowledge_base_id>
type  = HASH
field = artifact_id
value = Artifact JSON
```

一个知识库的全部成果保存在同一个 Redis Hash 中。没有独立索引 Key，因此不需要
Redis 事务、ZSET 或 Redis Cluster Hash Tag。

### 4.2 Artifact JSON

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| schema_version | integer | Redis 数据结构版本，初始为 `1` |
| artifact_id | string | 成果稳定 UUID，与 task_id 分离 |
| knowledge_base_id | integer | 所属知识库 |
| artifact_type | string | briefing、mind_map |
| title | string | 成果标题 |
| status | string | queued、running、succeeded、failed |
| task_id | integer/null | 内部执行 Task ID |
| assistant_subtask_id | integer/null | 本次生成对应的 Assistant Subtask ID |
| content | string/null | 简报 Markdown 或 Mermaid 文本 |
| source_document_ids | integer[] | 发起生成时的文档 ID 快照 |
| generation_config | object | 补充要求及生成配置快照 |
| error_message | string/null | 用户可理解的失败原因 |
| user_id | integer | 创建人 |
| created_at | string | ISO 格式创建时间 |
| updated_at | string | ISO 格式更新时间 |
| completed_at | string/null | ISO 格式完成时间 |

Artifact ID 使用应用生成的 UUID，不使用 Redis 自增序列。失败重试时保持
Artifact ID 不变，只替换 `task_id` 和 `assistant_subtask_id`。

### 4.3 读写方式

- 创建、更新：`HSET key artifact_id artifact_json`。
- 查询详情：`HGET key artifact_id`。
- 查询列表：`HGETALL key`，由应用层按 `created_at` 倒序排序。
- 删除单个成果：`HDEL key artifact_id`。
- 删除知识库全部成果：`DEL key`。

单条 `HSET`、`HDEL` 和 `DEL` 命令本身具有原子性。MVP 不维护第二份索引，
因此不需要 `MULTI/EXEC`。

### 4.4 存储边界

- Artifact Key 不设置 TTL。
- 不增加独立权限或成员表。
- 不增加草稿、审核和发布状态。
- 不增加文件夹、标签和收藏。
- 不增加独立的思维导图文件表。
- 不增加 PPTX 文件或附件存储。

### 4.5 Repository 边界

新增统一接口：

```text
ArtifactRepository
├── create()
├── get()
├── list_by_knowledge_base()
├── update()
├── update_status()
└── delete()
```

MVP 实现为 `RedisArtifactRepository`。API、权限、Subtask 对账和输出解析均依赖
Repository 接口，不直接拼接 Redis Key。未来迁移到 MySQL 时不改变 API 和前端协议。

现有 `RedisCache` 会按缓存语义吞掉读写异常，且没有 Hash 接口，不直接复用。
`RedisArtifactRepository` 独立封装 Redis Hash 操作，失败必须向上抛出并返回 503。

### 4.6 运行假设与局限

- Redis 由 DBA 团队维护，容量能够覆盖 MVP 数据规模。
- Redis 已配置持久化，实例重启不会丢失数据。
- 应用侧不再为 Redis 高可用、备份和恢复新增实现。
- `HGETALL` 会读取知识库的全部成果，并由应用层排序；MVP 预期单知识库成果量较小，
  暂不增加分页索引。
- Artifact JSON 更新采用最后写入生效。MVP 假设同一 Artifact 的并发修改较少；
  如果后续出现覆盖冲突，再在 Repository 层增加 CAS 或拆分字段。

## 5. API 设计

建议新增独立端点文件：

```text
backend/app/api/endpoints/knowledge_artifacts.py
```

并在 `backend/app/api/api.py` 中使用 `/knowledge-bases` 前缀注册。

### 5.1 创建成果

```http
POST /api/knowledge-bases/{knowledge_base_id}/artifacts
```

请求：

```json
{
  "artifact_type": "briefing",
  "title": "产品资料简报",
  "document_ids": [101, 102],
  "instruction": "突出核心结论和下一步行动"
}
```

规则：

- `title` 可空，由服务端生成默认标题。
- `document_ids` 为空时，服务端解析当前知识库全部可用文档。
- 服务端始终保存最终文档 ID 快照。
- 没有可用文档时返回 422。
- 文档不属于当前知识库、索引未完成或用户无权访问时返回 422。
- 服务端生成 UUID 作为 `artifact_id`。
- 创建成功后立即返回 queued Artifact。

### 5.2 查询列表

```http
GET /api/knowledge-bases/{knowledge_base_id}/artifacts
```

规则：

- 按 `created_at DESC` 返回。
- MVP 默认返回最近 50 条，不做复杂筛选。
- 使用 `HGETALL` 读取后在应用层排序。
- 查询时批量对账 queued/running Artifact 的 Assistant Subtask 状态。
- 返回 `can_manage`，供前端控制生成和管理入口。

### 5.3 查询详情

```http
GET /api/knowledge-bases/{knowledge_base_id}/artifacts/{artifact_id}
```

返回完整 `content` 和来源文档快照。

### 5.4 重命名

```http
PATCH /api/knowledge-bases/{knowledge_base_id}/artifacts/{artifact_id}
```

MVP 只允许修改 `title`。

### 5.5 重试

```http
POST /api/knowledge-bases/{knowledge_base_id}/artifacts/{artifact_id}/retry
```

规则：

- 仅 failed 状态允许重试。
- 复用原来源快照和生成配置。
- 创建新的隐藏 Task。
- 保留 Artifact ID，替换 `task_id`、`assistant_subtask_id` 并清空旧错误和结果。

### 5.6 删除

```http
DELETE /api/knowledge-bases/{knowledge_base_id}/artifacts/{artifact_id}
```

使用 `HDEL` 删除 Redis Hash 中对应的 Artifact：

- 不删除关联 Task。
- 关联 Task 使用 background 类型；普通任务列表必须明确排除该类型。

## 6. 创建与执行流程

### 6.1 来源解析

`ArtifactService.create_artifact()` 负责：

1. 使用 `can_manage_knowledge_base_documents()` 校验创建权限。
2. 查询知识库所有 `index_status=success` 且可用的文档。
3. 用户传入文档 ID 时，计算其与可用文档的交集并严格校验。
4. 未传入时使用全部可用文档。
5. 将最终 ID 列表写入 `source_document_ids`。

生成 Task 始终使用这一快照，后续知识库新增、删除或重新选择文档不改变已发起成果。

### 6.2 生成器注册表

服务端维护固定映射，不允许前端指定执行智能体：

```text
briefing → 预制 Notebook 智能体 + 简报固定提示词
mind_map → 预制 Notebook 智能体 + Mermaid 固定提示词
```

注册项至少包含：

- 智能体名称和 namespace。
- 固定 Prompt 模板。
- Task 类型。
- 输出解析器。

当前默认 `wegent-notebook` 使用 Chat Shell 并配置了 Mermaid Skill，可以承担简报和
思维导图。二期如增加 PPT，再创建预制 PPT 智能体，并通过相同 API 触发其 Task。

### 6.3 复用 Task 执行

Artifact 服务不直接调用模型，也不新建 Celery 任务。

建议从现有 WebSocket `chat:send` 流程中抽取一个可复用的服务入口，按顺序完成：

1. `create_chat_task()` 创建 Task、用户 Subtask 和助手 Subtask。
2. `link_contexts_to_subtask()` 创建 `selected_documents` 上下文。
3. 调用现有统一触发逻辑进入 ExecutionDispatcher。

Task 元数据：

```text
type=background
source=knowledge_artifact
taskType=knowledge
artifactId={artifact_id}
```

要求：

- 复用同一条上下文预处理和权限链路。
- 不从 Artifact API 反向调用 WebSocket。
- 不从后端通过 HTTP 调用自己的 `/v1/responses`，直接组合内部执行服务。
- 不复制一套 Task/Subtask 创建逻辑。
- 不在请求中等待生成完成。

### 6.4 跨 Redis 与 MySQL 的一致性

Redis Artifact 与 MySQL Task 无法原子提交。MVP 按以下顺序缩小不一致窗口：

1. 完成权限和来源文档校验。
2. 生成 `artifact_id`。
3. 使用 `HSET` 写入 queued Artifact。
4. 创建隐藏 Task，并将 `artifactId` 写入 Task 元数据。
5. 回写 Artifact 的 `task_id`、`assistant_subtask_id` 和 running 状态。

失败处理：

- Redis 首次写入失败：不创建 Task，接口返回 503。
- Task 创建失败：将 Artifact 标记为 failed。
- Task 已创建但 Redis 回写失败：保留 Task；查询时可根据 Task 元数据中的
  `artifactId` 修复 `task_id` 和 `assistant_subtask_id` 并继续对账。
- 删除知识库时：直接 `DEL knowledge-artifacts:<knowledge_base_id>`。

MVP 不增加 Redis 事务、分布式事务、补偿队列或定时修复任务。

### 6.5 固定输出约定

为减少新工具开发，MVP 使用固定 Prompt 和类型化解析器：

| 类型 | Task 输出约定 | Artifact 结果 |
| --- | --- | --- |
| briefing | 最终助手消息为 Markdown 正文 | `content` |
| mind_map | 最终助手消息只包含一个 Mermaid 代码块 | 提取代码写入 `content` |

如果 Task 完成但结果不符合约定，Artifact 标记为 failed，并返回“生成结果格式不正确，请重试”。

MVP 不增加 Artifact 回调 Tool，不解析任意自然语言文件链接。

## 7. 状态对账

### 7.1 状态映射

| Assistant Subtask 状态 | Artifact 状态 |
| --- | --- |
| PENDING | queued |
| RUNNING | running |
| COMPLETED 且结果解析成功 | succeeded |
| COMPLETED 但结果解析失败 | failed |
| FAILED、CANCELLED、DELETE | failed |

### 7.2 读时对账

`GET artifacts` 和 `GET artifact detail` 执行以下逻辑：

1. 找出当前返回范围内 queued/running 的 Artifact。
2. 按 `assistant_subtask_id` 批量查询对应的 Assistant Subtask。
3. 更新状态。
4. Assistant Subtask 进入终态时调用类型化解析器。
5. 使用 HSET 回写包含 content、error_message 和 completed_at 的完整 Artifact JSON。
6. 返回最新结果。

这样不需要新建定时任务或完成回调。代价是 Redis 中的状态可能在下一次查询前保持旧值，MVP 可以接受。

## 8. 前端设计

### 8.1 文件组织

建议新增：

```text
frontend/src/apis/knowledge-artifacts.ts
frontend/src/types/knowledge-artifact.ts
frontend/src/features/knowledge/artifact/
  components/ArtifactPanel.tsx
  components/ArtifactCreateDialog.tsx
  components/ArtifactList.tsx
  components/ArtifactSaveDialog.tsx
  components/ArtifactViewer.tsx
  hooks/useKnowledgeArtifacts.ts
  hooks/useArtifactPolling.ts
```

### 8.2 工作台改造

现有 `DocumentPanel` 已包含文档和权限 Tab，最小改法是扩展为：

```text
文档 | 成果 | 权限（有权限时）
```

- 文档 Tab 继续渲染现有文档区域。
- 成果 Tab 渲染 `ArtifactPanel`。
- 权限 Tab 沿用现有条件展示。
- 保留现有面板折叠、拖动宽度和 localStorage 逻辑。
- `KnowledgeDetailPanel` 继续持有 `selectedDocumentIds`，同时传给 ChatArea 和 ArtifactPanel。
- 不增加第三栏。

### 8.3 轮询

新增 `useArtifactPolling()`，沿用 `useDocumentIndexPolling()` 的模式：

- Artifact 列表存在 queued/running 时，每 5 秒刷新。
- 全部进入终态后停止。
- 切换知识库或组件卸载时清理定时器。
- 不增加 WebSocket 订阅。

### 8.4 两种预览

#### 简报

- 使用 `EnhancedMarkdown` 渲染 `content`。
- “保存为知识库文档”使用轻量 `ArtifactSaveDialog`，复用 `WysiwygEditor`、附件上传与文档创建 API。
- 弹窗允许修改标题与正文，默认保存到当前知识库根目录；目录选择不纳入 MVP。

#### 思维导图

- 将 `content` 传入现有 `MermaidDiagram`。
- MVP 验收只要求成功查看。
- 不新增导图文件存储、编辑器或导出逻辑。
- 现有 MermaidDiagram 已有的交互能力可以保留，不为缩减范围专门删除。

## 9. 权限

所有权限必须在服务端校验，前端 `can_manage` 只控制展示。

| 操作 | 权限 |
| --- | --- |
| 列表、详情、预览 | 能访问知识库 |
| 创建、重试、重命名、删除 | `can_manage_knowledge_base_documents()` |
| 简报保存为知识库文档 | 复用现有文本知识文档接口权限 |

Artifact 查询必须使用 `knowledge_base_id` 和 `artifact_id` 组合定位 Redis Key，
并始终通过 MySQL 中的知识库记录校验访问权限，禁止只凭 Artifact ID 返回数据。

## 10. 异常处理

| 场景 | 处理 |
| --- | --- |
| 知识库不存在或无访问权限 | 返回 404，避免暴露资源存在性 |
| 无文档管理权限 | 返回 403 |
| 没有可用来源文档 | 返回 422 |
| 来源文档不属于当前知识库 | 返回 422 |
| 预制智能体未配置 | 返回 503，并且上线前不得展示对应卡片 |
| Redis 不可用或写入失败 | 返回 503，不返回空列表、不静默降级到内存 |
| Task 创建失败 | Artifact 标记 failed |
| Task 完成但结果格式错误 | Artifact 标记 failed，可重试 |
| 删除 Artifact | 只删除业务记录，不影响底层 Task |

## 11. 实现顺序

### 第一阶段：公共闭环

1. 新增 Artifact Schema、Redis Repository、Service 和 API。
2. 实现 Redis Hash 的创建、查询、更新和删除。
3. 接入隐藏 Task 创建与来源上下文。
4. 实现 Assistant Subtask 状态及结果读时对账。
5. 实现 ArtifactPanel、列表、创建对话框和轮询。
6. 使用 briefing 跑通完整纵向链路。

### 第二阶段：思维导图

1. mind_map 复用 MermaidDiagram。

### 第三阶段：收尾

1. 简报接入 ArtifactSaveDialog。
2. 增加中英文文案和埋点。
3. 完成权限、失败重试、响应式和回归测试。

## 12. 测试范围

### 后端

- 创建时权限校验。
- 文档范围解析和跨知识库文档拒绝。
- Redis Hash 的创建、查询、更新和删除。
- Artifact Key 不设置 TTL。
- `HGETALL` 后应用层排序。
- Assistant Subtask 状态映射。
- 简报和思维导图结果解析。
- 失败重试替换 task_id 和 assistant_subtask_id。
- Task 已创建但 Redis 回写执行 ID 失败时可读时修复。
- background Task 不进入普通任务列表。
- 删除不触发 Task 删除。

### 前端

- 来源与成果 Tab 切换。
- 创建请求携带当前 selectedDocumentIds。
- 活动状态开始轮询、终态停止轮询。
- 简报和思维导图 Viewer 路由正确。
- 只读用户看不到生成和管理操作。
- 知识库切换后不保留上一知识库的成果与来源选择。

### 最小集成验证

必须使用真实后端请求验证：

```text
简报：选文档 → 生成 → 轮询完成 → 阅读 → 保存知识库
脑图：选文档 → 生成 → 轮询完成 → Mermaid 可见
```

## 13. 审阅重点

已确认 Redis 作为 MVP 的 Artifact 永久事实源，不新增 MySQL 表。实现时需重点确认
两个问题：

1. 是否接受“Task 是执行引擎，Artifact 是知识库级业务索引”的对象关系。
2. 是否接受使用查询时对账代替新的完成回调或定时任务。

除以上两点外，MVP 不建议继续增加新的基础设施或抽象。

为降低未来迁移成本，Redis Key 和序列化细节只能存在于 Repository 层；
API DTO 保持稳定，每条记录携带 `schema_version`。后续若改用 MySQL，只替换
Repository 实现，不改变前端协议和 Artifact 业务模型。
