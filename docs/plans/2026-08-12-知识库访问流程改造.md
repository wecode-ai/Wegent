# 知识库访问流程改造

本文以本次开发开始时的 `wecode-ai/main` 为对照：“改造前”指基线实现，“本次改造”指本文所述变更，“改造后”指变更落地后的状态。

## 1. 知识库的使用方式

从用户角度看，知识库会从不同入口进入任务。入口决定“用什么知识”和“使用多久”；后面的方案才决定“如何查询这些知识”。

| 使用入口 | 用户操作 | 使用范围 | 本次改造的关系 |
| --- | --- | --- | --- |
| Chat 中选择知识 | 从知识选择器中选择 Wegent 知识库、文件夹、文档，或钉钉知识空间、文件夹、文档 | 以本次明确选择为准，并可在后续任务中恢复 | 是本次改造的主要场景，选择信息会完整传到 Chat 或 ClaudeCode |
| 智能体使用默认知识库 | 在智能体中预先绑定 Wegent 知识库 | 当前消息没有明确选择 Wegent 知识库时，使用智能体的默认知识 | 已绑定的 Wegent 知识库会进入改造后的访问流程；本次不新增外部默认知识库 |
| 任务或群聊绑定知识库 | 把 Wegent 知识库绑定到任务，或在任务中选择外部知识 | 绑定关系随任务保留，供后续消息使用 | 内部和外部绑定都会转换成统一的选择信息 |
| 知识工作台中提问 | 在知识库详情页或 Code Wiki 中打开工作台，可进一步选择文档 | 默认使用当前 Wegent 知识库；选中文档时缩小到对应文档 | 当前知识库和文档范围会进入同一访问流程；简报、思维导图等生成任务仍保留自己的严格文档范围 |
| Chat 中通过文字或链接指定钉钉 | 在问题中说明要查询钉钉，或直接粘贴钉钉文档链接 | 这是消息内容，不会自动变成知识选择器中的结构化范围 | 系统会根据钉钉特征加载对应能力；有链接时，模型可按链接读取内容 |
| 订阅或自动化任务使用知识库 | 在订阅配置中选择 Wegent 知识库 | 每次定时或事件触发执行时，使用订阅中保存的知识库 | 会复用任务的 Wegent 知识访问流程；本次不新增外部订阅知识源 |
| 通过 OpenAI 兼容 API 使用知识库 | 调用 Responses API 时传入知识库名称或 `knowledge_base_refs` | 当前请求可指定整库、文件夹或文档；未重新指定时可继承任务已保存的范围 | 解析后的 Wegent 范围会进入同一访问流程；本次不为该 API 新增外部知识引用 |

这些入口遵循以下规则：

1. 当前消息明确选择了 Wegent 知识时，本次选择优先于任务绑定和智能体默认知识库。
2. 没有明确选择 Wegent 知识时，使用任务已绑定和智能体默认的 Wegent 知识库。
3. 工作台中当前打开的知识库会自动参与，用户选中具体文档后优先使用更小的文档范围。
4. 通过选择器选中的外部知识会作为任务知识保留；问题中的钉钉文字和链接只属于当前消息。
5. 订阅使用已保存在订阅配置中的范围；API 请求中新传入的范围优先于该任务之前保存的范围。

以下情况不单独算作新入口：

- 公开智能体仍属于“智能体默认知识库”。
- 后续对话、重试和流水线续接属于任务中已选知识的继承。
- 知识库摘要、简报和思维导图是工作台内部对知识的使用。
- Backend 内部检索接口是上述入口的实现方式，不是独立的用户入口。

本次改造的核心，是让上述入口得到的知识选择能够稳定进入 Chat 和 ClaudeCode。它不扩展智能体可配置的知识类型，也不会把粘贴的链接自动保存为知识资产。

## 2. 改造前如何访问知识

改造前存在两类处理方式：

```text
Wegent 内部知识
  -> Backend 准备知识范围
  -> Chat Shell 加载通用知识工具
  -> 查询 Wegent 知识库

钉钉等外部知识
  -> 前端保存选择或链接
  -> 通过问题关键词推测需要的能力
  -> 尝试让模型访问外部系统
```

这套实现能够支持部分场景，但没有完成从“用户选择”到“实际读取”的稳定连接。

### 2.1 选择信息不完整

- 外部知识可以没有明确的知识库 ID，部分代码用 `all` 代替。
- 钉钉文档发送时会变成普通链接，知识空间和文件夹信息随之丢失。
- 去重、历史恢复和后续任务无法始终还原用户的真实选择。

### 2.2 选了外部知识，不代表已经连上对应系统

改造前主要根据问题中的关键词推测需要加载哪个能力。即使用户已经选了钉钉文档，只要问题中没有出现“钉钉”，对应工具仍可能不会加载。

### 2.3 Chat 和 ClaudeCode 的表现不一致

Chat 和 ClaudeCode 的执行方式不同，改造前没有向两者提供同一份知识选择信息。同一个选择可能在 Chat 中生效，在 ClaudeCode 中丢失或表现不同。

### 2.4 新旧工具可能同时生效

如果增加外部系统的原生工具后，仍然保留原有的通用知识工具，模型会同时面对两套访问方式，容易重复读取或选错工具。

### 2.5 合并和展示规则不一致

同一个知识库可能同时选中整库、文件夹和文档。不同环节的合并规则不完全相同，会导致重复发送、历史记录重复展示，或遗漏文件夹下的子文件夹。

## 3. 可选方案对比

不同方案没有绝对优劣，它们分别适合不同的产品目标。

### 3.1 方案一：由 Backend 统一查询多个来源

```text
用户选择多个来源
  -> Backend 将选中的知识库、文件夹和文档绑定为查询范围
  -> 只在该范围内查询各个系统
  -> 合并、去重和排序
  -> 把统一结果交给模型
```

**查询范围**

用户在知识选择器中选中的内容，就是 Backend 允许查询的范围。模型可以调整搜索词，但不能通过提示词换到未选中的知识库，或扩大到未选中的文件夹和文档。

如果用户在问题中要求查询选定范围之外的内容，Backend 不应自动扩大范围。用户需要先在知识选择器中补充来源，或通过受控接口明确更新选择，系统重新检查权限后才能查询。

**适用场景**

- 必须保证每个选中来源都被查询。
- 需要明确展示哪些来源成功、为空或失败。
- 需要跨来源的统一排序和引用。

**优点**

- 可以保证多来源的查询覆盖。
- 查询始终限定在用户明确选中的范围内，提示词无法绕过。
- 模型只需要使用一套查询工具。
- Backend 可以统一处理部分失败、去重和重排。

**代价**

- 每接入一个新来源，都要在 Backend 适配搜索、读取、分页、权限和错误处理。
- 用户不能只靠一句提示词临时扩大查询范围，需要额外的选择更新和权限检查流程。
- 不同系统的搜索分数和结果粒度本来就不同，强行统一可能隐藏差异。
- 外部系统的超时、限流和授权问题都会进入核心查询流程。

### 3.2 方案二：直接连接外部系统

```text
用户选择来源
  -> Wegent 加载对应的 Skill/MCP
  -> 模型调用外部系统的原生工具
  -> 模型整理结果
```

**适用场景**

- 临时查看一篇文档或少量外部来源。
- 内容变化频繁，需要查看当前内容。
- 资料不允许长期复制到 Wegent。
- 需要完整使用外部系统的特有能力。

**优点**

- 用户选择后可以立即提问，无需等待导入和索引。
- 不长期保存外部内容副本。
- 新来源可以复用自己的工具，接入成本较低。
- 外部系统新增能力后，不必先改造 Wegent 的统一查询接口。

**代价**

- 同时选择多个来源时，主要由模型决定调用顺序并整理不同格式的结果。
- 不能天然保证每个选中来源都被查询。
- 不同来源较多时，模型需要面对更多工具和不同的结果格式。

### 3.3 方案三：导入 Wegent 后统一查询

```text
用户选择外部资料
  -> 明确发起导入
  -> Wegent 下载、解析和索引
  -> 后续使用 Wegent 知识工具查询
```

**适用场景**

- 资料要成为智能体的长期默认知识。
- 内容会被频繁、重复查询。
- 需要稳定的查询速度、统一的召回效果和可复现的结果。
- 允许在 Wegent 中保存一份受管理的副本。

**优点**

- 所有内容使用相同的解析、索引、权限和查询方式。
- 导入完成后，查询不受外部系统临时故障影响。
- 更适合长期管理、重复使用和评估优化。

**代价**

- 导入内容是快照，不一定与外部系统的最新内容一致。
- 用户需要等待下载、解析和索引。
- 需要处理刷新、重试、重复导入、删除和外部权限变化等问题。
- 能够读取外部文档，不等于有权将它复制到组织知识库。

### 3.4 三种方案的关键差异

| 对比项 | Backend 统一查询 | 直接连接外部系统 | 导入 Wegent |
| --- | --- | --- | --- |
| 回答依据 | 外部系统的当前内容 | 外部系统的当前内容 | Wegent 中的导入版本 |
| 查询范围 | Backend 强制限定在选中范围 | 由选择说明引导，最终取决于外部工具权限 | 仅查询已导入内容 |
| 多来源整理 | Backend 负责 | 模型负责 | 通过 Wegent 索引统一查询 |
| 内容新鲜度 | 高 | 高 | 取决于导入或刷新时间 |
| 新来源接入 | 需要 Backend 适配 | 注册 Skill/MCP | 能稳定获取文件或正文即可 |
| 外部内容副本 | 不长期保存 | 不长期保存 | 会长期保存 |
| 实现成本主要在 | Backend 查询和聚合 | 选择、连接和模型调用 | 导入、索引和同步 |

## 4. 为什么本次改造选择直接连接外部系统

本次要解决的是 Chat 和 ClaudeCode 即时访问外部知识，而不是建设跨来源搜索平台，也不是把外部资料自动变成 Wegent 知识资产。

在这个目标下，直接连接外部系统是最小且足够的方案：

1. 可以读取当前内容，没有导入延迟和版本滞后。
2. 可以复用 Provider 已有的读取、搜索和权限能力。
3. Backend 只需要知道用户选了什么、应该连接哪个系统，不需要理解每个来源的搜索结果。
4. 新 Provider 可以通过注册 Skill/MCP 接入，避免持续扩大核心知识流程。

因此，改造后的责任划分是：

> Wegent 负责保留用户选择并连接正确的外部系统；内容读取、搜索和权限判断由外部系统负责。

## 5. 本次改造的具体变化

| 改造前的问题 | 本次改造的处理 |
| --- | --- |
| 外部引用可以没有明确的知识库 ID | 每个引用都必须有来源系统和知识库 ID |
| 钉钉选择发送后只剩普通链接 | 完整保留知识空间、文件夹和文档信息 |
| 根据问题关键词猜测需要的能力 | 根据实际选择加载对应的 Skill/MCP |
| 工具缺失时可能继续执行 | 执行前检查配置，无法连接时明确报错 |
| Chat 和 ClaudeCode 获取到的选择信息不一致 | 生成同一份选择说明交给两种执行方式 |
| 原生工具和旧通用工具可能同时存在 | 原生能力生效后，不再加载旧通用工具 |
| 整库、文件夹和文档容易重复 | 统一去重，选中整库时覆盖其下子项 |
| 选中文件夹可能遗漏子文件夹 | Wegent 文件夹默认包含所有后代 |
| 个人与组织中的同名资源可能混淆 | 保留所属范围，并用它参与去重和展示 |
| 用户配置和系统部署配置混在一起 | 区分两种配置，支持部署方注册新 Provider |

代码中使用 `SelectedKnowledgeRef` 保存“用户选了什么”。该对象只统一选择信息，不统一各 Provider 的查询参数和返回结果。

## 6. 改造后方案的边界

### 6.1 用户选择不是强制的权限限制

用户选择的范围用于告诉模型应该查看哪里，但最终能访问哪些内容，仍由外部系统的账号权限决定。

选择知识只表示需要读取，不表示用户授权修改。改造后仍依靠任务说明和外部系统权限防止误写。如果以后要从机制上禁止写入，需要只向模型提供只读工具。

### 6.2 不保证查询每一个选中来源

模型会根据问题决定使用哪些来源。改造后方案不强制所有来源都被查询，也不统一各来源的结果排序。

当产品明确需要完整覆盖、并行查询和统一排序时，再引入 Backend 统一查询方案。

### 6.3 不自动导入外部内容

选择外部文档只代表本次任务可以访问它，不会在 Wegent 中创建副本，也不进行解析和索引。

需要长期保存的资料，应由用户明确选择“添加到 Wegent 知识库”，再走独立的导入流程。

### 6.4 本次只覆盖 Chat 和 ClaudeCode

其他 Shell 需要在工具接入和选择信息传递方式就绪后再支持。
