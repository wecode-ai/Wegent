# 协作权限架构与不可破坏的规则

空间决定管理范围，项目默认继承空间成员，资源通过明确授权参与项目。所有列表和操作使用同一套服务端权限判定。本文是经用户确认的产品契约；测试验证这些规则，不能为了通过测试而降低规则。

项目详情与项目列表复用同一条权限查询和响应构造路径（CP13），保留空间继承角色与权限来源。个人分身配置保存在所选 Executor，本地保存和启用不查询云端权限、智能体目录、模型目录或目录就绪状态。Issue 发起的个人任务和分身任务使用相同的 Issue 执行权限，不要求项目设备绑定或初始化项目环境；实际绑定云端 Issue 时仍由服务端检查当前用户的执行权限。`stand-in-personal-task` 桌面 E2E 以普通成员和零设备绑定验证手动任务与分身任务均在当前设备完成，并纳入共享桌面 CI。

主分身与静默后台统筹复用当前用户已授权的 Wework 能力。项目空间仍执行服务端资源权限与派发范围校验，插件和工具写操作继续走原生审查；事件和工作内容不是授权。任务调度仅操作当前账号和设备的任务，不自动回答用户输入或审批，也不提高被续聊任务的权限。批次派发意图执行前重新校验角色、连接、指派和启用时间。

用户与个人分身的直接会话默认复用 Codex 原生 Guardian 审查技术操作；启动、恢复、分叉和续轮使用同一审查者配置。Executor 不代答审批卡，也不把业务时间或范围的回答转换成执行许可。只读执行边界、连接范围、业务操作的 `askBeforeAct`、配置确认和登录授权保持原路径；来自外部连接及委托工作的人工确认策略不因此改变。原生工具审批使用结构化协议元数据，普通业务表单和 URL 授权仍由用户处理。CP01–CP20 不变。

项目统筹以项目、小组、启用成员和承载设备记录责任归属。同一项目小组只保留一个启用绑定，启用、停止和显式接管通过当前 generation 比较更新；绑定保存不创建私人会话。项目成员、Agent 与设备的使用权限继续独立校验。派发及模型任务凭据使用启用成员的执行身份，源定义所有者、设备所有者及 Runtime 身份保留各自职责。

远程执行区分目标设备的模型引用与本次任务明确提交的模型接口。前者始终重新校验目标设备当前模型目录；后者仅由服务端鉴权后的 Runtime RPC 绑定当前用户、实际 Runtime 设备、任务及命令，不能用客户端自报的来源替代。接口密钥只保留在该任务命令的内存绑定中，不写入目标的全局模型目录或任务快照。续跑使用相同绑定；进程重启后凭据不可恢复时，明确要求重新选择接口。命令重放不能改变原接口配置。CP01–CP20 不变。

项目统筹命令复用 Issue 指派、小组任务准备和现有执行队列。服务端生成的不可变输入摘要与命令 ID 绑定，已经接受的执行记录作为回执优先返回；重放不能修改输入或重复创建执行。新派发在同一事务检查绑定、项目与小组版本、成员及资源权限，并通过 Issue 版本比较保留并发编辑和已有指派。事务内授权读取复用当前连接，单连接 MySQL 回归覆盖完整提交、资源撤销、重复命令及写入失败后的回滚。领取和负责人决策另外校验当前绑定；独立短事务可观察已提交的撤权，并保留调用方事务。运行中的撤权记录取消请求，等待 Runtime 确认停止。`test_project_coordination_authority.py` 与 CI 注册的 `project_coordination::mysql_tests` 保护这些服务端协议约束。

项目统筹启动 Codex 或 Claude 轮次前，用请求自带的执行凭据校验当前命令及资源授权，并比较完整的持久命令上下文；此只读校验不会派发工作。负责人后续轮次在当前进程内保留启用成员的原始身份，原本缺失的凭据不得替换成设备登录凭据。这些凭据不进入任务索引；进程恢复后缺少原身份时，必须先完成授权恢复，不能切换执行人继续派发。命令回执读取首次接受的事实，当前授权读取最新执行尝试，以兼容现有隔离重试机制。

本地项目也复用原小组执行队列，保留 Issue 级执行占用及原生审批、模型和工作区策略。命令回执关联现有执行记录，不创建第二套队列。指派标识贯穿负责人、成员和人工交付；显式改派会使旧标识失效，正常轮次交接保留它。领取、请求启动、Native 实际启动及后续轮次都检查当前 Issue 与绑定。未启动的 Native 排队项在持久移除后通过原取消回调释放执行占用；已运行的任务只请求停止，并等待实际结果确认。创建和指派人工子任务也记录原启用成员，仍等待原交付流程。

项目事件由自有 DSH Router 程序化归集，项目负责人对话中的自动统筹入口只在明确启用后生效。静默评估使用独立、临时且禁用工具的 Codex 轮次，只接收有权查看的项目、Issue 和公开评论，不读取私人聊天、记忆、Agent 提示词或账号配置。模型只返回结构化意图；Executor 持久化意图并通过原队列提交具体工作，不能代答人工输入或审批。需要补充的信息仅对启用成员展示，返回原 Issue 补充；发布到项目仍须显式操作。

禁用工具的评估复用 Executor 现有隔离 Codex 运行器，在进程启动时限制能力目录和工具注册，结束后退出；仅覆盖共享进程的线程配置不足以建立此边界。模型选择、提供商认证、取消和原任务队列保持原有路径。模型协议验证同时检查顶层与输入中的增量工具定义。

本地项目审批沿用本地会话身份与实际执行智能体创建者的比较，启用成员仍是派发和执行的审计身份。小组审批按当前执行 ID、同一 Issue 的智能体消息及当前项目智能体记录识别创建者；缺失或存在歧义时不提供入口，不以小组负责人或历史执行替代。云端仍沿用服务端审批授权。桌面验证通过原 Issue 批准执行、读取结果并由用户验收完成。

后台上下文和临时任务按绑定 generation 隔离，迟到的旧读取、注册与回调不能覆盖新绑定的批次。受版本冲突或已不可访问 Issue 影响的未接受意图重新读取当前源后再判断；已接受命令优先恢复原回执。只读评估中断可以重新判断，不能据此重放业务操作。`project_router` 回归保护代次隔离、真实队列回执恢复、Issue 归档恢复、静默窗口和状态读取权限，桌面 CI 的 `project-coordination` 检查点覆盖显式启用、问题回原 Issue、审批保留、接管和停止。

## 归属与角色

```mermaid
flowchart TD
    User[用户] -->|成员及角色| Space[空间]
    Space -->|唯一归属| Project[项目]
    User -->|直接邀请| Project
    Project --> Issue[Issue]
    Issue --> Result[评论、交付物、执行与会话]
    Owner[资源所有者] -->|共享使用| Catalog[空间资源目录]
    Catalog -->|项目管理员启用| Binding[项目资源绑定]
    Binding --> Agent[智能体]
    Binding --> Runner[执行设备]
```

管理角色只有管理员、成员和只读成员。API 使用 `Maintainer`、`Developer`、`Viewer` 表达；所有者由空间归属关系确定，响应中的 `Owner` 是只读的所有者标识，不能通过成员接口赋予。项目创建者是审计信息；创建项目时明确添加创建者为项目管理员。

新项目、父空间授权和创建者的管理员授权在同一事务中写入。新项目的父空间授权直接插入，不对不存在的授权记录加锁，避免不同空间并发创建项目时产生 MySQL 间隙锁死锁。资源授权按资源与实体的唯一标识原子创建或恢复，再锁定已存在的记录；保留原授权 ID、审批历史与外层事务边界。MySQL 权限回归套件覆盖并发项目创建、不同资源和同一资源的并发授权、唯一父空间及创建后的使用权限。

| 空间身份 | 默认继承项目 | 受限项目 |
| --- | --- | --- |
| 所有者 | 管理员 | 管理员 |
| 管理员 | 管理员 | 管理员 |
| 成员 | 成员 | 单独邀请 |
| 只读成员 | 只读成员 | 单独邀请 |
| 项目访客 | 项目直接授权 | 项目直接授权 |

空间所有者和管理员始终拥有所属项目的管理权。对其他用户，有效的项目直接角色优先于空间继承角色，可以提升或降低项目权限；移除项目直接授权后恢复当前空间继承权限。仅修改项目职责不创建角色覆盖，也不批准待审批或已拒绝的授权。公开浏览是单独的读取授权，不自动将浏览者加入负责人或协作小组名单。

## 权限契约

本地参与发现使用服务组合层确认的范围：本机归属主体 `0` 与当前已验证账号主体；这不是全局用户别名，也不改变云端授权。快筛、统一待办、只读原生 pending 提示和本地 inbox 使用同一范围；空闲时不新增 inbox 轮询，提示失败为未知而非空列表。新评论由组合层注入的当前实际作者写入，历史 sender 不变。答复仍要求精确 `recipient == persisted comment.sender`，例如接收人 `0`、当前作者 `7` 时必须显式转派后再答，不因发现范围包含两者而放宽 claim。既有小组、已读与任务启动权限继续使用其授权身份，不被存储归属 `0` 覆盖；CP01–CP20 不变。

问题分派仍要求当前 Issue Developer 权限及责任人、小组负责人或 Maintainer 身份；仅作为问题报告人不产生分派权限。报告与阻塞标记先核验本人有效默认命名空间 Device，再以原活动持久执行 ID 校验同一项目、Issue、原 Runtime task、设备及 `executor_owner_user_id`；同名自有设备不能证明拥有别人的 Runtime。只有手工绑定、或小组 Runtime 尚无精确 canonical 执行证据时返回 409，不猜测 owner 或按会话命名补身份。请求标识使用原活动持久设备身份，切换同设备别名不会重复创建问题。

问题报告源可以通过显式 `set_blocking` 操作更新是否阻塞，但仍须具备当前 Issue Developer 权限，并同时匹配持久记录的报告人、原 Runtime task 和本人拥有的原设备身份。此权限不包含分派、取消或答复；请求不得混入接收人或取消字段。行锁内校验 pending 状态与版本，仅更新阻塞标记、版本、更新时间和 `blocking_changed` 事件，保留接收人、责任人及本轮等待起点。普通分派权限与原生操作审批保持不变；缺失来源证据不补猜身份，CP01–CP20 不变。

Issue 中已精确指派的业务回答只续接可信持久原执行的授权身份，不将答复人视为私有机器人的新使用者。接收人仍独立通过当前 Developer、Issue、原评论线程和 Runtime 绑定校验；入口与队列都重新验证原 assigner 的当前资源权限，答复归因保留为实际答复人。缺失原执行授权证据的绑定拒绝续接，不用 Runtime owner 或答复人推测身份。普通评论与新执行的授权规则保持不变。`test_human_reply_execution_authority.py` 覆盖跨人私有机器人续接、普通使用拒绝、撤权、错误接收人/线程/Runtime、队列身份及缺失来源拒绝；不授予私有 Runtime 或凭据访问，CP01–CP20 不变。

| 编号 | 不变量 |
| --- | --- |
| CP01 | 每个项目有唯一、有效的父空间；归属与成员授权分别保存。 |
| CP02 | 空间所有者和管理员管理所有所属项目，包括受限项目，与项目创建者无关。 |
| CP03 | 默认项目继承成员和只读成员；受限项目停止这两类继承。 |
| CP04 | 仅加入项目不获得父空间资源、成员或其他项目权限。 |
| CP05 | 空间所有者和管理员保留项目管理权；其他用户的有效项目直接角色优先于空间继承角色，移除直接授权后恢复继承；待审批、拒绝、未知角色、失效空间和归档项目不提供权限。 |
| CP06 | 创建者、负责人、小组组长和设备账号不产生额外的人类管理权限。 |
| CP07 | Viewer 能读取空间及有权访问的项目，不能修改、评论、指派或执行。 |
| CP08 | 项目成员列表包含继承和直接成员，返回有效角色、直接角色、来源及来源空间；空间继承角色只读，项目管理员可为继承成员设置或移除项目直接角色。 |
| CP09 | 已启用共享项目智能体对项目读者可见；显式 private 定义保持仅创建者可见和可用；离线或配置问题以状态和原因表达。 |
| CP10 | 资源使用授权不授予修改原定义或读取私人凭据的权限。 |
| CP11 | 项目派发使用智能体和设备必须满足有效资源使用授权及项目启用关系；旧版合法安装关系在原项目内保留使用效力，不扩展资源目录或原定义权限。个人任务及分身使用自己的 Executor 不要求项目设备绑定。 |
| CP12 | 项目派发的固定设备、项目池和用户选择只改变调度，不绕过项目资源授权；个人任务及分身沿用个人执行路径。 |
| CP13 | 列表、详情、创建、修改、指派、评论启动、自动化派发与设备领取使用相同的授权规则。 |
| CP14 | Issue 读取先检查项目权限，再检查 open/related；项目管理员可读全部 Issue。 |
| CP15 | 执行检查当前 Issue 访问和执行能力；项目派发另检查启用绑定和资源授权，个人任务及分身不要求项目设备绑定；快照不能替代当前授权。 |
| CP16 | 撤权阻止新派发和领取；正在运行的任务请求停止，收到 Runtime 确认后才标记停止。 |
| CP17 | 移出空间撤销空间成员关系及其所有下属项目直接授权；需要继续作为访客时重新邀请。 |
| CP18 | 撤销空间资源授权使所有下属项目绑定失效；保留历史数据并显示失效状态。 |
| CP19 | 空间所有权可以转交，历史创建者保持不变；项目的治理权不依赖历史创建者。 |
| CP20 | 权限判定返回来源和拒绝原因；前端不能独立授予服务端拒绝的能力。 |

分身、连接消息与 Issue 派发执行使用 Codex 原生基础权限：自动模式继承 `:workspace`，允许正常文件读取、工作区与临时目录写入；操作前确认模式继承 `:read-only`。两者均保留网络访问，使已启用插件资源和 CLI 配置可正常读取。文件系统可读不代表允许提取凭据或访问无关私有数据，来源内容仍不能授予额外权限。越界操作必须经当前原生审核器批准：自动模式使用 AI 审核，确认模式使用单次人工确认。批准后该次命令实际提权，拒绝后不得执行；不得使用全局根目录 `deny` 使批准失效，也不得将批准变成后续命令的永久权限。此执行策略由用户明确授权，CP01–CP20 的服务端成员、资源使用及凭据隔离契约保持不变。

`stand-in-workspace` 桌面 E2E 通过真实 Codex、shell 和 GitHub CLI 验证插件资源读取、合成且不含凭据的 CLI 配置读取、联网、默认越界写入拒绝、AI 批准后的真实越界写入及拒绝后的不执行。`stand-in-action-confirmation` 使用真实 `connection_work` 来源验证人工批准前文件不存在、批准后文件创建。只模拟模型和审核模型响应；不读取个人登录文件，不声称验证了真实 GitHub 登录。

GitHub/GitLab 仓库与个人来源使用更严格的原生边界：本地工作区分析和修改继承 `:workspace`，模型 Shell 默认不能联网；账号绑定的只读 MCP 工具在宿主执行，外部写入逐次人工原生确认。不能通过关闭角色确认设置放宽此边界。合并需明确交办并绑定 head SHA。接收、读取、确认和接管均校验用户及设备代次；Webhook 验签不授予执行权限。此扩展不改变 CP01–CP20。Executor 的 Git 权限契约测试覆盖网络、审核器和工具审批，`stand-in-git` CI 场景覆盖真实内部服务的协议边界，不声称验证真实平台登录。

## 授权与执行

```mermaid
sequenceDiagram
    actor Member as 项目成员
    participant API as 任一操作入口
    participant Policy as 统一权限服务
    participant Queue as 持久化队列
    participant Prepare as 队列消费者
    participant Runtime as 执行设备
    Member->>API: 创建、指派或启动执行
    API->>Policy: 检查项目、Issue 和资源绑定
    Policy-->>API: 允许及来源 / 拒绝及原因
    API->>Queue: 保存执行意图
    Queue->>Prepare: 准备已提交的评论执行
    Prepare->>Policy: 检查当前授权与执行配置
    alt 配置冲突
        Prepare->>Queue: 记录任务失败，保留已保存评论
    else 配置有效
        Prepare->>Queue: 等待有权设备上线领取
    end
    Runtime->>Queue: 领取工作
    Queue->>Policy: 重新检查当前授权
    Policy-->>Queue: 当前允许 / 授权已撤销
    Queue-->>Runtime: 原子认领的工作
    Runtime-->>Queue: 接收、开始及终态证据
```

派发人、智能体定义所有者、设备所有者和 Runtime 会话身份分别记录。资源所有者共享的是明确的使用能力；模型与连接凭据仍由原有凭据权限和执行身份管理。项目访问只授予所属 Issue 的会话读取权，不授予整个设备的任务目录。

评论入队先检查当前用户、Issue 与智能体的使用授权；Runtime 配置、模型和环境绑定由队列消费者准备，失败属于执行记录。待准备意图不授予设备使用权，准备和领取都必须重新校验当前资源授权。`test_queued_comment_execution.py` 覆盖只读成员、私有定义和已撤销资源的入队拒绝，以及入队后撤权、配置失败、人工审批、离线领取和未领取会话的提前回复；这些测试使用隔离数据库和合成执行状态，不代表真实 Runtime 联调。

桌面普通会话与已绑定 Issue 的会话均注册 `wework_space`，不再根据消息中的云链接决定是否提供工具。Codex 沿用与内置浏览器相同的原生延迟工具发现，Claude 默认启用原生工具搜索；初始化只提供简短路由说明，不读取项目、Issue 或评论，详细流程随工具描述按需加载。未绑定时 `get_current_context` 返回 `bound: false`，由 `list_spaces` 和显式目标参数发现资源；绑定仅提供默认目标。无绑定上下文仅在后端、凭据和能力面完全一致时复用；绑定授权始终使用独立上下文。跟进回合仅在 MCP 配置或审批边界变化时重载线程，保持后台进程存活；进程重启和线程卸载会清除已加载配置记录。工具调用继续校验实际资源权限与派发范围；人工领取和分身任务通过人工分配标识使用个人执行权限，派发 ID 仅关联流程而不授予智能体角色；显式智能体角色仍校验派发范围，角色无效或缺少项目、Issue 时拒绝启动。`project-space-tool-discovery` 桌面 CI 检查点覆盖普通会话的延迟发现、显式读取与评论持久化；MCP 单元测试覆盖初始化不取数、授权拒绝和派发边界。

从 Issue 创建的个人任务以原项目和 Issue 作为默认上下文，可以通过 `wework_space` 显式指定当前用户有权限访问的任意项目和 Issue，按实际权限读取、修改、指派或评论。会话起点不构成额外的访问边界，服务端继续校验目标项目和 Issue 的权限；访问其他项目或 Issue 不改变原会话或交付物绑定。Issue 会话统一使用协作上下文，不按私人任务或分身任务增加写入限制；用户任务及已配置职责所需的回写、改派和交付无需因共享 Issue 写入而另行确认。内置协作 MCP `wework_space` 的服务器与单工具策略均免于工具审批，包括分身自动模式与操作前确认模式；外部工具仍遵守原生审批，协作工具继续执行服务端实际权限校验与派发角色边界。`stand-in-personal-task` 桌面检查点同时断言协作读取、评论和指派完成后没有 AI 审核记录。`wework/src/features/todo/workItemRuntimeContext.test.ts` 保护该上下文契约。协作执行成员默认限定在派发 Issue 和执行类工具内，并允许下述直接父项只读例外；协作管理者保留项目内管理权限。`executor/src/task_runtime/mcp/issue_access_tests.rs` 覆盖同项目和跨项目的本地读写、云端读写与评论、服务端读写拒绝及默认上下文保持，角色边界由同模块现有契约测试保护。

个人分身连接插件继续使用现有外部来源内容约束和操作确认机制。新的 `connection_work` 与历史 `dingtalk_work` 均不能从来源内容取得额外权限。分身作为独立身份运行，不再引用个人或项目智能体；旧绑定迁移先将原项目限制与已选范围取交集，保留排除项和确认策略，再删除绑定字段，不扩大既有授权。`personal_stand_in_contract` 覆盖旧格式、幂等持久化、版本冲突和授权交集；CP01–CP20 保持不变。连接记忆按用户、Provider、账号和资源精确隔离，钉钉迁移保留原记忆范围及去重身份。`stand_in_identity_contract` 覆盖迁移和 Provider 隔离；Codex 确认契约同时覆盖两种工作来源以及默认和命名 Home。

受管 `wework_control` 不向 `stand_in_identity`、`connection_work`、`dingtalk_work` 或项目委托执行授予个人控制入口；这些执行保留各自的工具范围与操作确认。源会话持久化身份也参与校验，不能通过缺失来源字段取得个人权限。`workbench_control` 契约测试覆盖注入与源身份校验，HTTP 回归覆盖替身与控制 surface 隔离及各自会话关闭。个人调用方可以按现有权限续聊项目或替身目标；目标仍以原身份执行，不取得调用方的个人权限。跨设备续聊复用现有目标元数据、会话授权和发送接口，不新增权限或远控豁免。发送入口通过已有历史授权链路的 `identityOnly` 元信息投影取得原始身份、工作区与 Runtime，不加载消息正文或占用历史 CPU worker，按单条会话查询相同规则拒绝已归档或删除的目标，使用前端 materialize 相同的编译器；续聊统一调用既有项目/Issue 可见性和 execute 权限服务。目标 Runtime 强制保留派发角色和项目/Issue 绑定，替身确认机制仍然生效。回归覆盖源身份伪造、目标保留执行范围、设备拒绝及后端读写拒绝，拒绝后不会改用直接写 RPC。CP01–CP20 不变量不变。

本机 APP 会话的云项目绑定不会改变发送位置：复用既有 `/runtime-work/materialize` 完成原生或 Team 意图编译、资源和项目执行权限校验，再通过本机 Runtime 创建或续聊。创建和续聊共用当前项目/Issue 可见性与 execute 校验；仅绑定项目而未关联 Issue 时也拒绝 Viewer 执行。原生模型凭据仍由执行设备持有，Team 和云模型配置仍由后端编译；远端请求保留原有 APP 远控限制。已授权 IM 发送携带的内部 APP 消息授权同时用于读取目标原始身份，仍检查设备归属；普通 HTTP 读取、发送不能取得该授权。回归同时验证有权 IM 续聊、普通请求拒绝、创建和续聊的 Viewer/撤权/不可见 Issue 拒绝，以及本机 APP 云项目会话的附件创建、去重续聊和界面续聊。

新建会话只接受共享创建契约中的意图字段，执行身份和模型凭据由可信设备通道或原后端编译。会话引用不得将委托执行 fork 为个人执行。跨设备创建继续执行原后端的设备归属、资源权限、能力协商和 APP 控制策略；不会因新增工具放宽这些规则。本地项目空间绑定仍由本机存储和执行器处理。创建与控制回归覆盖上述分支、绑定清理、代理策略及来源隔离。

后台 MCP 桥只调用当前 Provider 声明依赖中的读取工具，不运行模型回合。工具归属同时核对完整插件身份；共享 App 服务另外核对 Connector 身份。缺少只读标注的旧工具可以由 Wework 适配插件声明精确读取契约，但不能覆盖明确的写入或破坏性标注。调用参数不能自授读取权限；后台授权交互取消后明确失败，不自动放行，也不改变分身执行时的确认策略。`connection_mcp_tests` 覆盖归属、读取边界、依赖变更和取消/超时清理，`stand-in-mcp` 桌面 checkpoint 覆盖真实 Executor 对跨依赖调用的拒绝。

没有 MCP 的插件可通过通用 CLI 读取传输复用已有 `localAuth.tool`。可执行工具、Connector、固定命令和允许参数均来自精确依赖及已安装 Wework 适配插件的读取声明；调用者不能传入命令或增加参数，也不执行 Shell 或 Skill 文本。钉钉采集已使用该路径，专用读取 RPC 已删除；回复继续沿用原来源绑定及确认策略。通用 CLI 契约测试与 `stand-in-cli` CI checkpoint 覆盖写入拒绝、参数注入和旧入口删除。

## 界面入口

子树归档与恢复在任何任务写入、外部提供方关闭或执行取消之前，逐项校验所有后代的编辑权限，保持 CP13/CP14。可编辑父任务不授予私有后代权限；拒绝时统一返回 404，不泄露后代信息，并保留原版本和排队执行。管理员保留全部子任务权限。`test_loop_item_archive_permissions.py` 覆盖原生项目及 GitHub/GitLab 协议，网页 `collaboration-project-views.spec.ts` 使用真实成员验证拒绝、无副作用及管理员归档恢复；既有 CP 契约不变。

云端 Runtime 历史读取的每个设备分块都在独立短事务中检查当前项目权限、Issue
可见性和持久会话绑定，遵循 CP14 与 CP15。鉴权 Session 在设备 RPC 前关闭，
不修改调用方事务；不能依靠重复 SELECT 或刷新 ORM 对象推进 MySQL REPEATABLE
READ 的旧快照。其他 Session 提交撤权或将无关联 Issue 收紧为 related 后，下一块
返回 404，且不再调用设备。现有 CI MySQL 权限套件用独立请求、写入和观察 Session
验证省略版本和 v1，断言旧请求快照仍存在、最新权限已拒绝以及 RPC 只调用一次。

Issue 关联的个人 Runtime 任务仅向任务所有者返回，变更请求关联也必须验证任务所有者。看板快照、分页关联任务和单 Issue 关联任务列表均按当前用户过滤；项目管理员身份不授予读取其他人个人任务的权限。仅有手动关联记录时，对话详情与搜索也必须验证所有者，不能以 Issue 可读权限替代个人任务权限。正式派发执行和协作成员活动继续使用各自的持久化执行授权。`test_project_board_snapshot_queries.py`、`test_runtime_session_device_identity.py` 和 Rust 关联任务查询测试保护这些边界。打开已归档任务前读取 Runtime 的明确归档状态，提示用户先恢复任务。

看板批量排序的 HTTP 与 MCP 入口共同遵守 CP07、CP13、CP14：Viewer 不能排序，其他成员只能提交和接收其可见的 Issue。可见卡片的重排只交换它们在全局同级顺序中的位置，保留不可见成员的位置；普通成员提交不可见或不存在的请求目标时，在写入前统一返回 404。项目管理员仍按既有规则查看全部 Issue。`test_loop_item_reorder_permissions.py` 覆盖角色、默认安全级别、同状态和跨状态排序，以及拒绝请求不改变持久化状态。

只有项目权限、没有父空间权限的用户，仍能从统一侧栏进入获授权项目。父空间只提供名称分组，不可打开空间主页或设置，也不暴露空间成员、资源目录或未授权的兄弟项目。公开项目的 Viewer 和直接邀请的项目访客都遵守这条规则；切换本地或云端空间、重复点击当前空间，不改变全局项目导航的授权范围。

- 空间管理：成员、项目目录、共享智能体、共享设备、空间小组和所有权转交。
- 项目管理：成员模式、有效成员与来源、访客、已启用资源、项目小组、自动化及 Issue 安全级别。
- 个人资源：原定义、个人设备、连接配置及共享授权。

个人目录 `GET /api/v1/resources?include_readiness=false` 只发现当前用户拥有的活跃智能体和设备。智能体只读取标识和名称元数据，返回 `status: unchecked`，不解析 Bot、Ghost、Shell、Model、运行凭据或模型依赖的组权限，也不展开列表未使用的 `workspace_ids` 和逐智能体设备 ID。设备仍返回选择器需要的身份、运行能力和在线状态。空间共享智能体继续使用经过空间权限校验的 `/api/v1/workspaces/{workspace_id}/agents`，不扩大资源可见范围。

目录中的“可选择”不承诺“可执行”。真正执行时仍重新检查当前资源授权和所选智能体的完整执行配置。未传 `include_readiness` 或显式传 `true` 的旧客户端继续获得原来的 `available` / `unavailable` 状态和绑定字段；新版网页和桌面共用轻量目录。

成员行必须区分有效项目角色、只读的空间继承角色和项目直接角色。项目中修改继承成员的角色会创建项目直接授权，不改变空间或其他项目的权限；移除直接授权后，成员行仍显示恢复后的继承角色。空间所有者和管理员的项目管理权不受项目直接角色影响。停用与删除分别表达绑定和原资源的生命周期。

## 不改表的存储与版本兼容

本次实现不增加表或列，不要求洗数据、批量改角色或重建项目。项目归属继续使用现有 `resource_members` 的 `CloudProject → workspace` 已批准关系，原关系的 Owner 标签保持不变；`workspace_id` 是查询属性，不是新增物理列。每次读取要求唯一父空间，缺失或歧义时拒绝授权，不猜测归属。

成员模式写入项目已有 `metadata` JSON 的 `membership_mode`，缺省为 `inherit`。新建项目同时写入旧后端识别的父空间关系。旧请求未提供新字段时不清空它们；旧代码若整体覆盖 JSON 仍可能丢失新设置，因此旧后端只能维持旧行为，不能承担新权限规则的实施。

已有角色读取时规范化：人类 Owner 为 Maintainer，Reporter 为 Viewer；空间真正所有者仍由 `Kind.user_id` 决定。旧请求中的 Owner/Reporter 接受同样的规范化，不能通过角色字段转交所有权。新空间 Viewer 在原关系中存为 Reporter，让旧后端的空间列表仍能识别；项目 Viewer 保持 Viewer。旧公开 Developer 关系在新后端仅授予 Viewer，原记录不重写。

资源使用分为两个有明确边界的版本：

- 新绑定记录 `authorization_version: 2`。直配定义要求 `Workspace → project_agent` 使用授权，CRD 智能体要求 `Team → workspace`，设备要求空间和项目的使用关系。
- 无版本标记的旧绑定保留原项目的安装授权。CRD 定义必须由记录中的安装者所有，内置定义沿用原规则；固定设备必须是旧绑定中明确记录、仍有效且由安装者所有的设备。不能凭个人所有权使用其他设备，也不会因此暴露空间目录。
- 新后端撤销旧资源授权时，先将相关绑定转为明确授权版本，或在项目 JSON 中记录固定设备撤权，再撤销共享关系。撤权后不能重新走旧安装路径。新绑定、待审批、拒绝或无效的显式授权不能使用旧路径。

创建或重新启用项目智能体时，只有已批准且具有使用角色的空间授权可以直接复用。显式共享仍需校验空间权限与原定义的共享管理权；校验通过后，在原授权记录上恢复批准状态和使用角色，再校验项目绑定，避免只读授权被误认为可用或待审批记录产生唯一键冲突。`test_project_agent_creation.py` 覆盖真实 Bot、Team 创建接口及授权恢复、拒绝分支；桌面 CI 的 `project-automation` 场景覆盖停用后重新授权并启用。

`creator_admin` 保留兼容输入，但共享项目绑定按项目权限展示。显式 `private` 保持仅创建者可见、可用；其他项目管理员也不能公开别人的私有定义。配置和私人凭据不自动共享。空间所有权转交时，若缺少历史创建者字段，只在本次操作中保存原所有者，不批量回填。

| 客户端 / 后端 | 行为边界 |
| --- | --- |
| 旧客户端 / 新后端 | 接受旧角色和智能体字段，沿用旧归属关系；由新后端执行统一权限规则。 |
| 新客户端 / 旧后端 | 缺少 `owner_user_id` 时不展示所有权转交；缺少 `membership_mode` 时不展示成员模式；资源目录先确认实际空间访问权。 |
| 旧后端 / 旧客户端 | 继续使用原表和原接口，执行原权限逻辑。 |
| 多版本后端混跑 | 数据格式兼容，但旧后端不会自动获得新规则。新权限能力上线前，相关请求需统一切换到新后端，或将同一策略回移到旧后端。 |

本地独享项目使用本地所有者权限，离线可运行；云端项目共享操作以服务端关系为准。

## 事故事实与恢复

开发服务会在启动时自动运行 Alembic。最初新增权限迁移被该服务自动执行，备份序列化失败；MySQL 保留了已执行 DDL，而项目归属回填回滚。原启动代码吞掉迁移失败，随后查询空的新父空间列，导致列表消失。此前“未迁移真实数据库”的报告不准确。

只读检查确认原 49 个项目记录和 49 条原父空间关系仍在，其中 29 个项目处于 active，未发生项目删除。当前代码已撤回新增迁移并恢复原关系查询，Alembic head 为 `f3a7c9e1b2d4`。失败尝试留下的两个未使用列和空备份表暂时保留，当前代码不读取它们；恢复过程没有继续执行 DDL、洗数据或批量改角色。将来清理这些遗留结构应作为独立数据库操作处理。

实际开发接口验证：admin 项目列表返回 200、27 个有权访问项目，空间列表返回 200、2 个空间。WebSocket 在 Python 直连和网关均能完成鉴权及项目订阅。首次连接失败后界面不再订阅的问题已修复：连接恢复时重新订阅，成功后清除错误，卸载和切换 Issue 时清理监听。

开发启动现在遇到迁移失败直接退出，不再带着不完整结构继续提供服务。

分配接收回执遵循 CP07、CP13、CP14 和 CP15：沿用项目及 Issue 读取权限，只允许当前分配的接收人确认本人已读；分身回执还需验证接收人所属设备上的当次任务绑定。回执只记录接收事实，不授予编辑、执行或资源权限。云端保存前在事务中重新检查活动分配，本地在同一 SQLite 事务中校验；转派后的旧请求不能确认新分配。定向回执测试和 CI 的 `stand-in-notifications`、`stand-in-cloud` checkpoint 覆盖身份、持久化及详情展示。

回执的高频读取复用 `loop_items` 中 `resource_type='assignment_index'` 的当前分配索引节点，以及现有的 `(parent_id, resource_type, sort_order)` 索引，再按分配事件主键读取回执。指派与撤销在事件事务内维护索引，所属 Issue 的行锁串行化转派与确认。存量 Issue 首次访问时在同一锁内一次性整理历史，随后不再重放动态；标记节点区分“尚未初始化”与“当前没有分配”。本地同样复用 `loop_items`，使用 `resource_type='issue_receipt'` 的小记录保存回执，按确定性主键定位；仅存量 Issue 首次读取时提取已有历史，后续不解析或重写 Issue metadata。不新增表、列、索引或数据库迁移。

新建 Issue 的首次指派在创建事务中直接写入事件和活动索引，不锁定尚不存在的评论或索引范围，避免不同项目并发创建时的 MySQL 间隙锁死锁。只有创建服务能选择首次指派路径；已有 Issue 仍在 Issue 行锁下读取最新指派、去重并重建索引。`test_issue_assignment_initialization.py` 验证首次写入不加历史范围锁且索引完整；CI 的 MySQL 权限回归套件验证不同项目并发创建及首次指派均可提交。

补报失败采用 5 秒起步、最长 1 小时的指数退避，调度状态在本地持久保存，重启不会重置等待时间。401、403、404、408、429 和服务器或网络失败均可在恢复后继续补报；成功及失效分配（409）完成出队。待发送记录最多保留 30 天，避免已删除 Issue 或永久无效绑定无限重试。分身确认前必须解析为当前有效、属于接收人的设备，停用设备的历史绑定不能用于确认。


空间智能体发现使用 `GET /api/v1/workspaces/{workspace_id}/agents?include_readiness=false`，保留空间可见性、源配置编辑权限与归属信息，批量读取所有者、设备授权与协作组织角色，返回 `unchecked`，不遍历执行依赖。外部身份提供方在请求内批量解析当前用户的组织角色，不跨请求保存权限结果。角色仅采用实际匹配的实体类型与实体 ID 所对应的授权，组织可见不代表拥有其他部门在同一组织上的角色；旧客户端的默认完整预检行为保持不变。

Namespace 成员授权按图分层批量读取，每个可达组织只访问一次，并从已验证的人员或外部实体成员关系传播。循环引用本身不产生权限，也不影响无关组织的解析；待审批和被拒绝的关系不参与传播。

Rust 项目成员名册通过三次批量查询读取父空间、人员授权和有效用户。计算结果保留 CP02/CP03 继承、CP05 空间管理权限、CP08 项目覆盖角色、权限来源顺序、待审批直接授权行标识，以及仅参与者可见的邮箱。真实 MySQL 回归覆盖受限项目、停用用户和撤权后的即时更新；这些列表读取不授予执行或源配置编辑权限。

里程碑遵守 CP07、CP13、CP14、CP20：项目读取权限是前提，Maintainer/Owner 管理里程碑，Issue 关联属于内容编辑（与分配混合修改时分别校验）。统计使用相同的 Issue 可见性过滤，归档的已完成 Issue 保留在完成统计中。关联校验与里程碑删除锁定相同记录，删除在同一事务中解除所有关联并推进 Issue 版本，不授予额外执行或资源权限。

里程碑计数的客户端查询按当前用户、项目角色、存储类型和默认 Issue 安全策略隔离。权限范围变化时立即隐藏旧范围的计数，并隔离未完成请求；新请求失败也不会重新显示旧权限数据。组件契约测试覆盖降权、读取失败和旧请求迟到。
