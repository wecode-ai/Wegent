# GitLab MR 修复任务集成

GitLab MR 集成把 Merge Request 的评审反馈（CI 失败、评审评论）自动转成项目空间看板上的**修复任务卡**，形成「评审 → 修复 → 重新提交 → 合并」的闭环。

## 功能概览

- MR 一有反馈（CI 失败或新的评审评论），看板就会生成一张卡，卡上带**给修复方（人或 AI）的任务说明**：MR 链接、源分支、评审意见、CI 失败摘要和历史迭代记录。
- 卡片随 MR 状态自动流转，无需人工维护。

## 接入方式

1. 在项目空间「任务来源」选择 GitLab，填入仓库地址和访问令牌（需要 `api` scope，建议同时勾 `write_repository`）。
2. 勾选/开启「接入该仓库的 MR」。创建流程勾选后会自动接入；也可以在项目管理页随时开关。
3. 开启后后端会在 GitLab 仓库上安装一个项目 Webhook（事件：merge_request / note / pipeline）。

> 令牌只保存在后端，用于调用 GitLab API；不会下发到执行 AI。

## 卡片生命周期

| 阶段 | 卡状态 | 触发 |
|---|---|---|
| MR 有反馈（CI 失败 / 评审评论） | 收集箱（未分配） | 自动建卡 |
| 分配给 AI / 人 | 进行中 | 分配时自动启动 |
| 修复已提交（push 新 commit） | 待确认 | push 后自动 |
| 新评论 / CI 又失败 | 进行中 | 新反馈自动 |
| MR 合并 / 关闭 | 已完成 | 自动 |

规则细节：

- **只有本轮新增的评论**才让卡保持在「进行中」；之前轮次的评论视为已解决，不卡着。
- CI 通过且无新评论 → 卡进入「待确认」，等人确认。
- 同一 MR 多次失败会**累积在同一张卡**上（历史区按轮记录，评论数显示「本轮新增」）。

## 卡片内容

卡片描述顶部有一段**任务说明**，随状态变化：

- 进行中：告诉修复方「CI 未通过 / 有评审意见，修好后 push 到源分支」。
- CI 已通过但本轮有新评论：明确提示「CI 已通过，但还有新评审意见要处理」。
- 待确认 / 已完成：说明无需再改 / 已合并。

下方是数据：评审意见（全部评论）、本轮 CI（失败 job + 日志尾部）、历史（最近几轮一行摘要）。

## AI 自动执行

- 卡片指派给项目机器人后，**每轮 actionable（CI 失败 / 新评论）会自动重触发一次运行**（新一轮从读最新卡片开始）。
- 自动重触发次数受项目设置的 `ai_automation.max_retry_count` 限制（默认 3），超过后停在「进行中」等人工介入。
- 机器人运行时通过 `get_board_item` 读取卡片（含任务说明），push 修复后 CI 自动重跑。

## 关闭集成

在项目管理页关闭「接入 MR」：移除 GitLab 上的 Webhook 并清理集成数据；看板上已有的卡保留。

## 备注

- Webhook 回调地址由后端配置的公开地址决定（内网部署时需保证 GitLab 能访问到）。
- 机器人目前不能直接把修复 push 回 MR 分支（执行器还没有为该类卡准备 clone/凭证）；「重新提交」那一步目前由人手动完成。
