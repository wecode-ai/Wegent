## 查看进程资源占用

<a id="process-explorer-controls"></a>

通过桌面原生菜单 **帮助 → 开发者工具 → 进程查看器** 打开独立的只读窗口。

| 操作       | 步骤与边界                                                                                                 |
| ---------- | ---------------------------------------------------------------------------------------------------------- |
| 筛选与分组 | 按名称、PID 或启动详情输入关键词；展开/收起所属对象的分组以定位窗口、执行器或插件进程                      |
| 资源与刷新 | 查看进程 CPU、内存、运行时长；页面定期采样，刷新按钮手动读取。汇总是列出的 Wework 进程之和，不是整机总占用 |
| 详情和复制 | 选择进程后查看并复制启动详情；分享前检查是否含私人目录或参数                                               |
| 列宽与置顶 | 拖动列头边缘调整宽度，双击恢复；使用置顶/取消置顶按钮保持窗口可见                                          |
| 错误与降级 | 查看不可用原因，刷新重试；部分进程信息不可用不等于应用没有运行                                             |

此窗口不提供终止进程操作。不要把查看进程与任务暂停、退出应用或清理用户数据混淆。

## 点击应用图标后没有窗口

再次点击 Dock 图标应显示已有的主窗口或启动恢复窗口，包括此前隐藏或最小化的窗口。
主页面加载完成即可显示；渲染器的健康确认用于升级事务，不再作为显示窗口的前提。
日志清理、托盘、附属窗口恢复、命令行工具安装和本地模型同步失败不应阻止打开桌面。

在 macOS 上，没有进行中的升级或回滚事务时，普通启动以实际打开的安装包为准。
手动替换应用后，旧版本选择、恢复桥或暂存目录不能把启动重新导向旧应用。
历史升级记录损坏时会记录警告，继续启动当前安装包；不要为解决启动问题删除任务目录。
原生恢复交接与版本目录中的恢复程序不属于普通启动：即使另一进程已完成回滚并清除事务，
这些入口仍须转交给活动版本，不能重新运行被回退的新版本。

如果仍无法打开，检查桌面日志目录中的 `wework-main.log`、`runtime-launch.log` 和
`dsh-core-runtime.log`，区分真实运行时故障与后台维护警告。数据迁移失败、缺少运行文件
或存储权限错误仍需要处理，不能通过清空用户数据来掩盖。启动动画、截图和窗口尺寸
异常只影响展示效果，不应阻止已加载的主窗口显示。

## 排查发布包的升级与回滚

使用发布工作流的诊断重放时，`app.log` 中的 `[desktop-e2e-startup]` 记录实际进程、
安装版本、活动版本选择和进行中的事务；`[desktop-e2e-relaunch]` 记录下一步启动的可执行文件。
结合 `release-state-result.json` 和 `activation-diagnostics.log` 判断磁盘版本选择与运行中的
安装包是否一致。诊断重放不会生成可用于发布的升级证明。
升级验收还会在回滚完成后实际启动已保留的目标包，覆盖携带和不携带原生恢复标记的延迟交接；
两种情况都必须回到旧版本，并继续使用原有任务。

本机验证必须隔离工作台 Home 和 macOS 原生 Home，不能移动个人应用数据来满足测试前提。
设置独立的 `HOME` 和 `CFFIXED_USER_HOME` 后，测试保留原生 Home 设置。

## 会话导出停留在打包中

查看桌面日志目录中的 `dsh-core-runtime.log`，按 `[wework-conversation-export]` 和导出任务 ID 查找最终写入阶段。日志分别记录文档同步、附件同步、打包和替换目标文件的开始、完成或失败事件，以及阶段耗时和附件数量，不记录文件路径或内容。若某个阶段只有开始事件，可据此继续定位对应的文件操作；不要仅因界面仍显示打包就判断导出已经失败。

## 页面出现错误或白屏

前端组件发生渲染异常时，Wework 会显示“Wework 页面出现错误”。点击 **刷新页面**
重新加载界面；尚未保存的内容可能会丢失。启动初始化失败时，也可以在错误页刷新重试。

如果刷新后仍出现错误，请打开调试面板查看日志，并附上复现步骤反馈问题。
如果渲染进程或整个应用退出后未能恢复，请重新打开 Wework。

## 模型不可用

- 在 **设置 → 模型** 检查 Codex 登录状态或本地模型地址。
- 确认选择的模型可以在当前设备运行。
- 使用代理时，保存设置后按提示重启 Codex。
- 本机官方 ChatGPT 模型因网络不可达而持续重连满 10 秒时，对话会显示当前模型和网络状态。
  短暂中断在 10 秒内恢复时不显示提示。点击 **设置代理** 可直接打开 **设置 → 代理**，
  保存本机代理后按提示重启 Codex。

### 模型容量已满

`Selected model is at capacity. Please try a different model.` 表示当前模型服务
过载，不代表任务代码执行失败。Codex 直连任务遇到结构化过载错误时，会保留
原会话和原模型，依次等待 5、10、20、40、60 秒自动恢复，最多 5 次；期间
可以停止任务。恢复不会重发原任务，也不会新增用户消息。

如果过载中断了正在进行的目标，自动恢复会继续原目标，保留目标内容、预算和
累计用量，并在当前轮结束后继续推进。等待恢复时暂停、删除或修改目标，会取消
这次目标恢复；不会重新创建目标或覆盖你的修改。
新建目标在首轮立即遇到过载时，也会显示阻塞状态，恢复后再更新为运行中。

若自动恢复后仍显示失败，可稍后点击 **重试**，或点击 **切换模型并重试**。
认证失败、额度不足和上下文超限不会按过载策略自动恢复。

### 后台终端历史

恢复会话后，后台终端保留已收集的输出，可使用 `Shift + PageUp` 和 `Shift + PageDown` 翻页。终端的屏幕阅读器行号和字符对齐信息随输出更新，持续输出和历史翻页不应阻塞其他界面操作。

### 恢复会话后工具不可用

部分 MCP 工具启动失败或连接中断时，在原会话继续发送消息会检查连接的实际状态并尝试恢复，保留原对话和健康的工具连接，无需重启应用。每次新执行最多协调恢复一次，并发续接合并恢复；同一执行不会循环重试。服务稍后恢复后，下一次续接仍可恢复连接。需要登录或重新授权的工具仍需完成对应授权。恢复连接不会自动重发之前的工具操作。

诊断日志 `codex MCP startup status` 记录进程代际、会话、服务、启动状态及脱敏错误；`codex MCP startup recovery` 记录实际触发恢复的服务。问题持续时，请保留这些记录。

### 无法连接模型服务

当本地模型代理未能向模型服务发出请求时，对话会显示 **无法连接模型服务**，并在错误卡片中直接列出连接失败的完整目标地址。`发送请求失败` 表示客户端没有收到可用的 HTTP 响应，通常应检查当前网络、VPN、代理或 DNS；如果地址属于公司内网，还应确认设备已连接内网或 VPN。

展开 **错误详情** 可以查看服务返回的原始错误。只有包含连接失败信息的 502 错误会显示为模型服务连接错误；服务已经返回但响应超时的普通 502 仍显示为请求超时。

## 项目无法打开

- 确认目录仍然存在且当前用户有读写权限。
- 远程项目应确认设备在线，并重新选择该设备上的目录。
- Git 项目目标目录已存在时，使用现有目录方式添加，或选择新的目标目录。

## Git 克隆失败

| 提示                             | 检查内容                           |
| -------------------------------- | ---------------------------------- |
| Authentication failed            | Git Token 是否有效、是否有仓库权限 |
| Repository not found             | 仓库地址和当前账号权限             |
| Remote branch not found          | 默认分支是否存在                   |
| Could not resolve host / timeout | 执行设备的网络和代理               |

## 任务或终端无法运行

- 查看当前设备状态；离线设备恢复连接后再试。
- 设备提示升级时，先完成升级。
- 切换任务后，确认终端对应的是当前项目或 Worktree。
- 重新打开应用后仍失败，可完全退出 Wework 再启动。

### 新任务未出现在侧边栏

开发调试时，可在 Wework Web Inspector 的控制台执行以下命令后复现：

```js
localStorage.setItem("wework:debug-runtime", "1");
```

前端日志中的 `[Wework] Runtime sidebar state` 会依次记录 executor 列表结果、状态合并结果，以及侧边栏排序和截断后的任务 ID。当前选中的任务存在于项目任务列表但未进入可见区域时，还会记录 `[Wework] Runtime sidebar selected task is hidden`。诊断完成后执行 `localStorage.removeItem('wework:debug-runtime')` 关闭详细日志。

## 无法审核或撤销变更

审核和撤销需要原执行设备在线，并保留该轮任务的变更记录。后续修改与原变更冲突时，先手动处理当前工作区，再决定是否回退。

## 内置浏览器异常

- 确认地址包含 `http://` 或 `https://`。
- 本地服务应确认进程和端口正在监听。
- 登录状态异常时，可以在 **设置 → 浏览器** 清理数据后重新登录。

## 云端连接失效

点击侧边栏的云端状态重新授权。确认 Backend 地址来自团队管理员，并且浏览器能够访问登录页面。

如果网络正常但云端状态偶尔显示不可用，先查看 Wework 前端日志中的以下记录：

- `[Wework] HTTP ... is still pending after 5000ms.`：请求超过 5 秒仍未收到响应，说明问题发生在等待响应阶段。
- `[Wework] HTTP ... completed slowly ...`：请求最终返回，记录总耗时、HTTP 状态码和传输方式。
- `[Wework] HTTP ... failed.`：请求没有收到 HTTP 响应，查看 `phase: "transport"` 下的错误。
- `[Wework] HTTP ... returned ...`：服务端已返回 HTTP 错误，查看 `phase: "http_error"` 下的状态码和错误信息。

每条请求都有 `requestId`。在桌面客户端中，该值会通过 `X-Request-ID` 传给 Backend；只有慢响应或 HTTP 错误诊断事件包含后端返回的请求 ID 时，日志才会记录 `backendRequestId`。用这两个 ID 可以把客户端日志与 Backend 日志关联起来。日志不会记录 Authorization、token 或请求正文。

## 获取帮助

在任意 Wework 桌面页面右上角点击 **反馈问题**，包括任务、新对话、插件、我的分身、已安排和设置页面。先填写问题描述（必填），可以在输入框中直接粘贴截图或文件，也可以点击 **添加附件** 通过文件选择器上传。确认问题描述后点击 **预览问题**，检查将要提交或导出的内容。

补充信息的默认行为如下：

- **诊断信息**（默认勾选）：Wework 和本地执行服务的运行日志、Wework 版本和系统信息。不含对话内容，隐私风险低；如果不需要，可以手动取消。
- **任务上下文**（默认不勾选）：完整对话记录原文和当前窗口截图。可能包含业务讨论、代码或屏幕上显示的任何内容，确认后再提供。
- **用户附件**：仅包含你主动粘贴或选择的文件，可能包含隐私内容。

如果勾选的某项内容不存在（例如新对话没有任务数据），导出时会自动跳过该项，并在预览中提示。

预览时可以展开任意条目查看内容。配置了反馈服务时，点击 **提交反馈** 提交问题；未配置反馈服务时，点击 **确认导出**，Wework 会把诊断包保存到系统下载目录。诊断包只在本机生成，不会自动上传。日志中的常见凭证和用户目录会被脱敏，但自由文本（如对话记录）无法完全脱敏，发送前应确认包内没有不希望共享的信息。

### 反馈提交失败

提交反馈时，原生日志会按问题编号记录以下事件：

- `Feedback submission started`：提交已开始，包含问题编号、脱敏后的目标端点和诊断包大小。
- `Feedback submission failed`：提交失败，包含失败阶段、耗时、错误类别；收到服务端响应时还会包含 HTTP 状态码。
- `Feedback submission completed`：提交成功，包含反馈单编号、反馈项 ID、是否为重复提交和耗时。

使用界面显示的问题编号搜索这些日志，例如 `report_id=WF-...`。日志中的端点只保留协议、域名、端口和路径，不包含查询参数或 URL 凭据；日志也不会记录反馈正文、任务上下文和附件内容。
