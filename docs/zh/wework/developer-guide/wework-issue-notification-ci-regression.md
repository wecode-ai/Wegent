# Issue 通知与人工任务 CI 回归

## 从其他入口打开 Issue 的已读同步

Issue 活动可见后，通过既有 `POST /v1/loop-items/{id}/read` 接口，
在同一事务中更新活动游标和当前用户关联通知的已读状态。
关联依据是通知 payload 的 `itemId` 或 `issueId`；其他 Issue、其他用户
及无 Issue 关联的通知保持不变，已读通知的时间戳也保持不变。
即使 Issue 内容此前已读，再次可见时仍确认已读，以消费随后到达的通知。
读取失败时保留未读计数；成功响应后立即刷新通知中心。

现有 CI checkpoint `collaboration-issue-comment-notification` 同时运行原导航场景
和独立的 `issue-notification-read` 场景。新增场景通过真实 Backend 建立三个
已读 Issue 和未读通知，依次从系统通知、深链、看板卡片打开，验证通知持久化
及应用内计数从 3 降到 0，无需手动刷新，且其他 Issue 的通知在打开前保持未读。
场景使用隔离 Electron 与数据库，由共享 runner 清理环境。
每次 Issue 深链沿用现有 `focusRequest` 传递新的打开请求；即使复用已打开的
抽屉，也会重新确认通知已读，同时保留活动滚动进度。场景最后在抽屉保持打开时
发送一条后续通知，再从系统通知打开同一 Issue，验证计数再次归零。

聚焦验证还覆盖重复读取、当前用户隔离、无关联通知、失败不刷新，以及已读内容
再次进入的情况。活动尚未加载或不可见时，不提前确认已读。

2026-10-27：隔离 Electron 的 `issue-notification-read` checkpoint 全部通过，
覆盖上述三个入口和同一抽屉的后续通知。Backend 的 4 条已读 API 回归通过，
通知中心及 API 37 条、活动及路由 146 条、共享滚动 19 条、checkpoint 契约 4 条通过。
测试夹具保留项目 ID 的字符串表示，避免大整数转换为 JavaScript Number 后丢失精度。

同轮 CI 的共享桌面产物构建等待了不存在的 Rust 镜像：消费端计算摘要时没有包含
生产端的 `backend-rs/examples/**`。桌面 CI 和缓存预热统一使用生产端的源码输入，
分类契约测试检查三处输入一致，避免通过扩大等待时间掩盖镜像标识不一致。

## 故障依据与修复边界

PR #3763 的提交 `f124f3d2e` 在桌面 Core 分片 12、15 失败：

- `project-assignment-notification` 的失败快照包含绑定 Task 的入口，
  但入口位于视口下方；可见元素点击命令不负责滚动。
  场景必须检查展开状态、等待任务行、滚动到入口后再点击，不能删除模型断言。
- `collaboration-issue-comment-notification` 首次深链高亮成功，
  重载后点击同一条通知不再高亮。同一地址没有产生新的定位请求，
  评论组件又按评论 ID 永久去重。

每次打开评论通知生成内部 `focusRequest`，由现有项目路由传到评论组件。
匹配已有页签时忽略此请求标识，避免重复页签。每个请求只滚动、高亮一次；
后台消息更新不重复高亮。快速再次点击时先结束旧动画，再在下一帧启动新动画。
不增加用户填写字段，不改变模型、设备路由或人工提交权限。

## QA 计划

环境：隔离的 Electron、真实 Backend/Socket.IO/设备，只有模型服务使用场景内的测试服务。
本地使用聚焦 Vitest 验证，完整桌面验收由现有 GitHub CI Core 分片执行；
不操作个人 WeWork 窗口，不通过重跑、扩大超时或跳过断言掩盖失败。

| 前置条件                           | 操作                                              | 预期                                                    |
| ---------------------------------- | ------------------------------------------------- | ------------------------------------------------------- |
| 人工 Issue 已绑定远程 AI 草稿 Task | 改变新会话默认模型，展开并滚动到已有 Task，再打开 | 使用绑定模型，不继承新会话默认值；原 Issue 仍由人工提交 |
| 评论通知首次打开                   | 深链定位目标评论                                  | 在原有时间预算内滚动并高亮，其他评论不高亮              |
| 重载后仍打开同一评论，旧动画已结束 | 从通知中心再次点击原通知                          | 复用页签，产生新请求，重新高亮并保存已读状态            |
| 高亮尚未结束                       | 快速再次定位同一评论                              | 重启动画，不延续旧动画的剩余时间                        |
| 定位请求没有变化                   | 后台消息刷新或普通重渲染                          | 不重复滚动和高亮                                        |
| 评论尚未加载，或已离开评论         | 加载目标评论；离开后再返回                        | 加载后定位；返回可以再次定位                            |
| 定位动画已排队                     | 卸载组件                                          | 清理动画帧和定时器                                      |

现有 CI 场景保留真实远程设备、任务绑定、交付、人工提交/验收、已读持久化断言。
失败时保留界面快照和运行日志，成功时检查截图。
场景使用各自独立的用户、项目和运行目录，交由桌面 runner 的清理流程回收。

## 同一处理人取消后重新指派

提交 `f5bbaab0c` 的 Core 分片 12 在人工验收后重新指派阶段失败：
`human_work.state` 仍为 `accepted`，场景要求新一轮指派为 `none`。
旧版 PATCH 接口只清空负责人字段，没有撤销活动流里的指派事件，
同一处理人的后续指派因此被错误去重。取消直接人工指派时复用现有
指派事件撤销服务，与负责人字段修改保持在同一版本校验事务内。

回归覆盖待验收、已完成 Issue 重新指派给原处理人或其他处理人；
新指派使用新事件 ID，保留 Issue 原状态，显式接手后才进入进行中。
未取消时重复指派仍幂等；版本冲突不撤销指派；工作流步骤的指派不被误删。
不删除已有验收记录，不改变桌面 E2E 断言或超时。

## 执行期间编辑 Issue 的版本冲突

PR #3869 的 Core 分片 9 在 `collaboration-local-agent-dispatch` 中失败：
返回 Issue 后标题仍是旧值。运行日志显示，标题保存的 `todos.update` 返回
`version_conflict`，后台执行状态同时推进了 Issue 版本；界面中的草稿值不代表
保存成功。

详情保存仅提交用户修改的字段。出现版本冲突时读取最新 Issue，确认这些字段
没有被其他编辑修改后，使用最新版本提交一次；同字段冲突、其他请求错误和
再次发生的版本冲突都保持失败。执行状态、优先级等未编辑字段不会被旧草稿覆盖。
只改处理人时不再先写入未变化的详情字段，直接使用当前版本执行分配。

聚焦回归覆盖执行状态变化与标题编辑并发、同字段冲突、网络错误、再次冲突、
空修改和处理人分配。现有桌面 E2E 的保存及返回标题断言保持不变，最终以修复
提交的 CI 结果验证真实集成。

## 协作成员首次活动的 MySQL 竞争

成员的运行事件可以先于活动记录到达。查找尚不存在的运行记录时，不应对 Runtime 二级索引执行 `FOR UPDATE`：InnoDB 的间隙锁可能与其他成员的首次插入冲突。先查找已有记录的主键，再对该主键执行锁定并刷新内容，既避免锁住未创建的成员，也保留已有活动的串行更新。

`backend/tests/integration/runtime_activity_mysql.py` 在真实 MySQL 的 `REPEATABLE READ` 下用同步屏障复现独立成员首次插入，并验证同一活动的并发更新不会丢失结果。平台 E2E 的第一个分片调用该验证；原有双轮协作 E2E 继续检查两个成员并行运行、完整成果及新经理任务。
