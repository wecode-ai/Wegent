# 停写后的升级准备与桥接版本

运行中的环境预热不能改写会话数据。桥接升级器在旧运行时停止、快照完成并写入现有
`ReleaseActivation` 后，由启动引导程序执行目标包的停写准备，再启动独立健康监督程序。
迁移耗时不计入旧启动器的 60 秒激活预算，真正的 runtime 和 renderer 就绪仍是唯一健康确认。

目标包在自身 `package.json` 声明 `weworkAfterStopPreparation: 1`，并交付
`dist/runtime/release-after-stop-cli.js`。桥接程序使用目标包自己的 Electron 执行入口，
请求绑定激活 token、目标 ID、包哈希和源 Workbench Home；不向子进程转交账号或任务凭据。
只有完整成功响应才能写入 `after-stop-ready.json`。目标引导程序在打开数据、启动 executor
或恢复 Goal 前校验回执；其他激活或其他包的回执不可复用。

复用现有激活日志，不引入第二套恢复事务。准备完成前中断且尚未试启动目标时，下次启动
重新执行目标的幂等准备入口。准备失败使用既有回退逻辑：兼容数据直接选择健康版本，
不恢复旧历史快照；不兼容且已经打开数据时，必须先取得原有恢复确认，再保留新数据并恢复快照。

桥接包只增加上述升级器能力，保持旧 Codex 和会话格式。后续目标才声明并执行数据迁移。
仅根据最小源版本不能认定兼容；旧包到桥接包、桥接包到目标包的升级和回退都必须以
交付包哈希、源码版本和 CI 验收证据确认。原生 API-key/账号、历史、Goal 和用户仓库的归属不变。
诊断构建和验证不会发布版本，也不会自动推广升级边。
