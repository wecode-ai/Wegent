# 自动化操作归因验证

## 用户故事与实现边界

作为项目自动化规则的创建者，我希望动态显示触发规则的名称，避免被理解为我手动转派或修改事项。

云端自动化创建、转派及状态变更的历史记录保存 `automation` 快照：
`rule_id`、`rule_name`、`run_id`。指派活动事件使用相同来源字段。
Python 事件处理和 Rust 后台调度均写入来源；共享活动卡片和历史列表优先显示规则名称。
原有授权用户和权限检查不变；这不是权限模型变更。
规则改名或删除不改写历史。没有来源快照的旧记录保持原状，不推测其触发者。

## E2E 场景

自动化用例位于 `frontend/e2e/tests/collaboration/automation-operation-attribution.spec.ts`，
由现有 Chromium CI 测试项目发现，不增加独立测试任务。

前置条件：隔离的真实 Backend、MySQL、Redis 和前端服务；已登录的规则创建者与另一名项目成员。
该用例使用人工执行目标，无需模型服务或模型替身。

1. 另一名成员创建事项，创建者配置一条状态触发规则。
2. 手动变更事项状态，等待该规则的真实指派记录落库。
3. 检查规则 ID、名称和运行 ID 已保存，授权用户 ID 仍是规则创建者。
4. 打开事项右上角「更多信息」，展开指派历史，操作来源显示规则名称。
5. 将规则改名并停用，再手动转派事项；刷新页面。
6. 历史自动操作仍显示原规则名称；新的人工操作显示操作者姓名，且不继承自动化来源。

清理：复用项目 fixture 的 `finally`，归档隔离项目和工作空间。
失败证据由既有 Playwright 报告保留；截图、日志及服务启动脚本不提交。

## 针对性回归

- Backend：覆盖自动化创建、指派、更新、规则改名后的快照和后续人工状态更新。
- Rust：覆盖后台来源快照、旧记录隔离、授权用户保留及指派响应序列化。
- 共享 UI：覆盖自动化/人工活动卡片、指派历史与状态历史。
- 继续运行现有指派与状态历史权限回归，确保归因不会替代授权身份。
