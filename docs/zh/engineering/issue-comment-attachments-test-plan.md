# Issue 评论附件回归验证

验证目标：Wework 将评论输入框中的本地附件上传到云端后，再保存评论和触发执行。评论中的附件引用必须属于当前 Issue，刷新后仍可读取原始文件。

## 环境与入口

使用现有桌面 runner 的隔离 Electron、真实本地 Executor、Python 后端、Rust 网关、MySQL 和 Redis。仅模型服务可模拟，不使用个人 Wework 会话或共享项目数据。

```bash
pnpm --filter wework e2e:desktop -- --segment collaboration-issue-comment-attachments
```

该 checkpoint 必须注册到 GitHub 桌面 E2E 的 Core 分片，单独运行时自行创建工作空间、云端项目和 Issue。文件使用有效 PNG 和不同的 ASCII 文件名，避免依赖独立的非 ASCII 响应头修复。

## 验证用例

| 用例           | 操作与预期                                                                                                     |
| -------------- | -------------------------------------------------------------------------------------------------------------- |
| 主评论带图     | 输入文字并添加 PNG，等待本地暂存完成后点击发送；评论成功持久化，云端附件引用存在，输入框清空，无附件归属错误。 |
| 回复带多图     | 回复已保存的评论，添加多个 PNG 并发送；回复仍属于原讨论，每个附件均上传且保存，执行收到云端附件 ID。           |
| 刷新与原始内容 | 刷新并重新打开 Issue；评论和回复中的附件引用仍存在，经认证读取附件时返回原始 PNG 字节。                        |
| Issue 隔离     | 打开同项目的另一个 Issue；其评论和附件列表不包含上述文件。                                                     |
| 上传或导入失败 | 定向组件回归使上传或附件导入失败；评论尚未发送，保留文字和附件，显示失败信息，恢复服务后可再次发送。           |
| 本地空间       | 定向组件回归确认本地项目继续使用本地附件，不触发云端上传。                                                     |

发表评论在上传和导入之后失败时，定向组件回归还应确认：恢复后重试复用同一云端附件 ID，避免重复保存图片。批量上传部分失败时，只重试失败文件。

## 证据与清理

记录失败前后的定向测试结果、桌面 checkpoint 日志及 GitHub CI 结果。成功断言应检查服务端持久化与附件字节，不能仅检查输入框清空。runner 退出时停止隔离进程并清理测试数据库、执行器目录和临时附件。
