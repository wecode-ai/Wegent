# Windows 完整版本更新与验证

## 用户结果与边界

应用内升级下载完整版本，不再打开 NSIS。工作台与本地运行时都成功启动后，才把候选版本设为当前版本。下载、校验、退出、启动任一步失败，不覆盖已确认可用的版本。任务、会话、用户插件、项目文件保存在原来的用户目录中。

0.4.x、0.5.x 已经发布的客户端不能事后改写。因此它们通过一次完整 NSIS 安装迁移到新协议；后续升级走新协议。已无法启动的旧客户端需要运行同一个完整安装包恢复一次。首次旧安装器迁移仍受旧 NSIS 卸载实现限制，不能宣称与新协议具有相同的断电保证。

本变更针对 Windows x64。macOS/Linux 保留现有发布与更新协议。持久化数据版本暂为 `1`；不同数据版本的候选包会在安装前被拒绝，不能把代码回退误当成数据回退。

## 已复现的旧协议问题

使用实际历史版本源码、真实 HTTP 与压缩包运行 `node wework/scripts/verify-windows-legacy-migration.mjs`，覆盖 0.4.1、0.5.10、0.5.12。目录内容摘要在历史版本中使用过 Windows 原生路径与 POSIX 路径两种格式，同一目录可以得到不同摘要；普通文件摘要不受此差异影响。新迁移描述使用普通文件凭据，绕开已发布客户端无法更改的摘要算法。

早期 0.4.x 尚无启动前的组件准备路径，精简安装包无法自行恢复缺少的执行器；清理旧托管组件缓存也会使依赖该缓存的精简安装无法离线启动。完整资源启动与清缓存恢复已加入自动化验证。以上是可检验的协议问题，不能据此断定每一次用户现场升级失败都具有同一个原因。

## 协议与责任

安装根 `WeWork.exe` 是独立 Rust 启动器；完整 Electron 位于 `versions/<version>-<manifest-hash>/WeWork.exe`。`release.json` 使用正斜杠相对路径，列出完整文件大小和 SHA-256；`windows-<channel>-v2.json` 提供完整 ZIP 的大小和 SHA-512。所有签名在清单生成前完成。

Electron 通过系统网络栈下载、解压和校验，退出前再次校验。原生启动器等父进程退出、持有操作系统文件锁、再次校验后发布不可变目录。升级期间 `update-state.json.active` 始终指向已确认版本；候选进程受进程组或 Windows Job Object 管理。只有运行时与页面都就绪，Electron 才写带随机能力值的健康确认。失败候选的整个进程树退出后，才能重新打开旧版本。原生启动器只在健康提交后安排原子自更新；普通启动仅重试已有替换请求，不隐式降级启动器。

完整 NSIS 只包含 `initial-update-state.json`，不包含运行中的 `update-state.json`。首次安装验证完整资源后初始化；覆盖安装通过 `--adopt-install` 读取新初始清单，完整校验新版本并验证现有状态的格式、路径和数据版本，再将新版本排为候选。旧版本文件已损坏或丢失时仍允许完整安装包修复；如果此时新版本也启动失败，会明确报告旧版本无法回退。中途解压失败或初始清单损坏不会覆盖旧运行状态。同版本重复安装保留原状态及已有版本目录。

退出交接先启动原生更新器，再停止本地服务。无法启动更新器时，当前应用继续运行；停服过程中失败则先撤销请求并确认更新器退出，再重启当前版本。原生端等待父进程结束后重新比对请求，已撤销或被改写的请求不能继续安装。

完整版本只读使用自己携带的组件，忽略旧 `managed-components/state.json`。清缓存只移除可重建内容；下次启动可离线重建。旧组件管理器保留给其它平台及已发布协议，不参与 Windows 新版组件激活。

旧 Windows 更新入口冻结为配对的完整 NSIS 地址与组件迁移描述。描述中七个组件均为普通文件迁移凭据，避免旧客户端原生路径与 POSIX 路径目录摘要不一致。凭据不会作为运行时代码激活，新版从完整安装资源启动。新的 v2 feed 独立滚动发布，不能被旧 feed 的版本检查阻挡。

#4101 的实际启动阶段进度、当前扫描/解压文件、软超时提示和启动失败诊断一并接入。主进程日志持久保存；失败页面支持复制已脱敏的诊断以及打开日志目录。日志写入失败不能阻断恢复操作。健康提交依赖真实页面和运行时就绪，与进度条显示百分比无关。

## QA 执行计划

每个 E2E checkpoint 单独创建隔离安装目录、本地项目、任务和模型回复；仅模型服务使用测试替身。真实 HTTP、文件系统、Electron、原生启动器与安装器不能替换为模拟实现。

| 验证项         | 前置与操作                                                                                                      | 预期与证据                                                                                           |
| -------------- | --------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 正常跨版本升级 | 启动真实版本 A，创建任务和回复，应用内下载完整版本 B 并重启                                                     | 无 NSIS；真实 `app.getVersion()` 为 B；旧目录保留；任务与回复仍在；状态、健康凭据、启动日志一致      |
| 损坏与不完整包 | HTTP 返回改坏的 ZIP；然后返回 ZIP 摘要正确但缺 `app.asar` 的包；同进程重试正确包                                | 两次拒绝且 active 不变；重试成功；并发下载只传输一次                                                 |
| 候选启动失败   | 真实 Electron main 提前退出，不发健康确认                                                                       | 停止候选全部子进程，恢复 A；不能把失败版本写入 active；保留任务                                      |
| 清缓存恢复     | 先成功升级，实际清理运行时缓存后重启，关闭云端连接                                                              | 完整安装内资源离线重建；仍为 B；任务与回复保留                                                       |

| 原生自升级     | 已确认版本提供新原生副本，等待旧 launcher 退出后执行替换；破坏副本再试                                          | 单次原子替换；失败仍有可用 root launcher；不撤销已健康的应用版本                                     |

| 安装中断       | 保持旧 live 状态，写入新 seed 和未完成版本目录；执行原生接管及普通启动                                          | 接管拒绝缺失/损坏文件；live 状态不变；普通启动忽略残留 seed，启动旧 active                           |

| 退出交接失败   | 实际执行缺失的更新器、停服中退出的更新器、停服失败、撤销后父进程退出                                            | 启动失败不先停服；停服失败确认取消后恢复当前版本；撤销的请求不会稍后误激活                           |
| 启动进度与日志 | 真实 Electron 执行阶段进度、慢启动、失败，点击复制诊断；实际工作台启动后读取持久日志                            | 阶段按顺序推进至 renderer、splash 关闭；软超时不误报失败；硬失败提供诊断；日志不可写时恢复入口仍可用 |

新协议 E2E 使用同源码构建的两个真实 Electron 包版本验证机制，不作为历史兼容性的证据。历史矩阵必须下载实际旧发布产物，并使用受信签名的迁移安装器。安装器签名不能为使测试通过而关闭。

运行入口：`pnpm --filter wework e2e:desktop -- --segment windows-update-install`，其它 checkpoint 为 `windows-update-validation`、`windows-update-rollback`、`windows-update-recovery`、`windows-update-migration`、`windows-update-reinstall`。先按 CI 步骤准备真实 Windows 包和 fixture。`wework-release-e2e.yml` 的 `suite=windows-update` 执行前四项，并用官方签名 0.5.10 安装包验证直接覆盖两次与后续 v2 升级；这条直接安装路径使用 CI 构建的未签名新 NSIS，不关闭任何生产更新签名校验。正式发布 CI 再使用真实签名 NSIS，对 0.4.0、0.5.10 和动态上一版执行迁移与重装矩阵；上一版已采用 v2 时按实际协议升级。原生测试：`cargo test --locked --manifest-path executor/Cargo.toml --test wework_launcher`。Windows 文件锁和 Job Object 结论必须来自 Windows runner；macOS 原生测试与隔离 Electron 冒烟不能代替。

测试结果写入正常 E2E result 目录，保留 Electron 日志、launcher JSONL、状态及断言结果。清理时先停止隔离进程，再删除对应测试目录；不能触碰个人 Wework、原生 Codex/Claude Home 或项目空间记录。

## 发布与运维限制

先发布不可变完整产物，再发布其 v2 feed。旧 Windows NSIS 与组件 feed 必须同版配对，首次迁移发布成功后冻结。新协议 ZIP 不依赖旧组件缓存，也不能混用旧 `WeWorkHostUpdate` 精简包。每次代码发布都必须提升应用版本；历史 runtime-only tag 不会生成新的 Windows feed。

安装根必须对当前用户可写。下载包验证完成后清理 ZIP；已安装版本保留上一可用版本。当前不自动删除更早的版本目录，避免删除仍被其它会话使用的可执行文件；磁盘不足会拒绝升级并保留当前版本。自动回收需要独立的目录使用权设计。

本机可执行 macOS 的原生事务测试、真实 HTTP 下载测试、发布脚本测试及隔离 Electron 冒烟。Windows E2E 和历史签名迁移的结果应以对应 CI run 为准，未执行时不得记为通过。
