# 看板自动化：交互与验收

验收对象是看板工单、经验配置、自动交办、人工结果和任务对话的完整闭环。核心宗旨见[做事经验与工单分派](../user-guide/board-automation.md)。本页是持续更新的验收契约；未附对应运行证据的项目不视为完成。

## 交付清单

最终交付必须包含测试通过报告、逐步交互报告、每步实际界面截图、架构图和时序图。测试报告记录命令、代码状态、环境、运行时间、退出结果和证据目录。交互报告逐步说明入口、操作、可见结果、保存状态和下一步。截图必须来自实际应用，并与步骤一一对应，不能用示意图代替运行证据。

## 架构与数据归属

```mermaid
flowchart TB
    UI[桌面看板与工单详情] --> API[工单与自动化 API]
    EDIT[经验编辑器] --> API
    API --> RULE[自动化定义：推进方式、角色、触发规则]
    RULE --> SNAP[工单经验快照：稳定目标、初始角色、当前交办]
    API --> START[启动与恢复服务]
    START --> MODE{快照推进方式}
    MODE -->|流程推进| SERIAL[按串行顺序选择角色]
    MODE -->|AI 推进| LEAD[协调者执行：目标、历史、参考角色图]
    LEAD --> DECIDE[交办 API：身份、版本、成员校验]
    SERIAL --> SAVE[同一工单保存交办与动态]
    DECIDE --> ACTION{交办动作}
    ACTION -->|角色、成员或图外执行| SAVE
    ACTION -->|完成| DONE[记录完成原因并停止自动推进]
    SAVE --> WHO{本次执行者}
    WHO -->|AI| RUN[既有执行服务：本机或云端]
    WHO -->|项目成员| HUMAN[工单等待人工结果]
    RUN --> ORIGIN{是否属于自动交办}
    ORIGIN -->|是| RESULT[核验本次交办，持久化结果]
    ORIGIN -->|否| ACTIVITY[记录独立任务结果，不推进自动化]
    HUMAN --> RESULT
    RESULT --> PAUSED{是否暂停}
    PAUSED -->|否| START
    PAUSED -->|是| HOLD[显示并保留结果，等待主动恢复]
    HOLD -->|用户恢复| START
    SAVE --> DB[(既有工单、执行、动态存储)]
    RESULT --> DB
    ACTIVITY --> DB
    CHAT[新增动态 / 回复动态] --> TASK[新建任务 / 继续原任务会话]
    TASK --> RUN
```

工单存储位置、代码工作空间、执行设备与会话生命周期是不同维度。云端工单的 AI 可以在本机或云端执行；回复动态继续其原执行会话。完成后的工单允许新建独立任务，该任务不重新启动已完成的自动化。

## 交办与回报时序

```mermaid
sequenceDiagram
    participant U as 用户
    participant I as 工单服务
    participant C as AI 协调者
    participant E as 执行服务或项目成员
    U->>I: 确认目标并启动经验
    I->>C: 启动协调回合，提供工单目标与参考角色
    C->>I: 交办请求（当前版本、角色/成员、事项、原因）
    I->>I: 锁定工单，校验协调者身份与版本
    alt 版本过期或交办仍在进行
        I-->>C: 明确拒绝，不产生新任务
    else 允许交办
        I->>I: 原子保存本次交办与动态
        I->>E: 按本次交办开始工作
        E->>I: 提交属于本次交办的结果
        I->>I: 拒绝旧交办覆盖，保存有效结果
        alt 已暂停
            I-->>U: 显示结果，等待主动恢复
            U->>I: 恢复
        end
        I->>C: 继续判断
        C->>I: 换角色、退回、交给人或完成
    end
```

### 交办 callback 回归计划（2026-09-09）

现场：`PRJ9755FA-2` 的执行 507 使用 Anthropic 模型，但 Runtime 将缺失的协议信息默认成 Responses；上游拒绝字符串 `tool_choice`。随后失败回报插入空 `client_message_id`，触发部署库 `uq_project_chat_client_message`，事务回滚，协调者继续看到运行中状态。

修正规则：交办成功即返回 `coordinator_handoff.end_turn`；协调者结束当前轮次，后端持有工作状态。成功、失败、人工结果由既有回报事务落库，再触发下一轮协调；下一轮明确携带 assignment ID、执行状态与结果。动态使用独立消息身份，重复回报由交办状态去重。云模型编译从同一 Model CRD 解析上游协议，不以调用方快照中的协议提示为准。

```mermaid
sequenceDiagram
    participant C as 分活 AI
    participant B as 后端交办服务
    participant W as 执行 AI 或人
    C->>B: 提交一次交办
    B-->>C: end_turn：结束本轮
    B->>W: 执行当前交办
    W->>B: callback：成功 / 失败 / 人工结果
    B->>B: 校验交办身份并持久化，重复回报不重复交办
    B->>C: 启动下一轮，携带已持久化结果
```

| 场景 | 环境、步骤 | 预期 |
| --- | --- | --- |
| C01 失败回报持久化 | 在隔离库添加现场同名唯一索引；交办后回报失败，再重放 | 两条独立动态；失败保留；重放不改变版本 |
| C02 协议一致 | 公有 Model 配置为 Anthropic/OpenAI；请求不带或带过期协议提示 | 编译协议与服务端 Model 一致，提供方凭据不暴露给设备 |
| C03 真实 callback | 独立 `event-center` CI 检查点；第一角色执行故意失败，下一轮重派并成功 | 协调者收到明确 callback 结果；三次决策分别交办、重派、完成 |
| C04 独立桌面复核 | `scripts/ai-verify.mjs` 隔离 Electron 执行 C03 并截图 | 与 CI 相同的实际状态转移，停止所有隔离测试进程 |

实现边界：`end_turn` 是工具回执和协调提示词的约定，不是 Runtime 强制终止指令；下一轮由服务端结果回报触发，复用现有协调启动、去重和恢复机制。没有新增数据表。
