# Collaboration permission architecture and invariants

## Group work ownership and optional resource sources

A Thread's work owner remains its Group. Groups can configure Agents, crews and explicitly authorized execution devices independently. Threads may also use independently authorized resources from their exact current linked Project. Classification does not grant resource access, and Group roles do not grant Project, definition, model credential or device permissions. Personal stand-ins remain available independently of shared Group configuration.

Agents use globally unique binding IDs; the persisted binding's `cloud_project_id` identifies its real source. Definitions are not copied and execution records are not rehomed to that source. When a crew is enabled in multiple containers, `assignee_group_source_id` explicitly selects the owning Group or exact linked Project. The execution snapshot records `binding_owner_id` separately from the definition's original `owner_type/owner_id`. Revocation refuses execution rather than falling back to another container's crew or Agent.

Cloud Group crews reuse `Kind(CollaborationGroup)` and explicit `CollaborationGroup/chat_group` grants. Group automation reuses `ProjectAutomationRule/Run` storage and dispatch rather than a second configuration copy. Inline Group Agents use `CollaborationChatGroup/project_agent` grants; Team and Device grants use their original resource types with `chat_group`. New grants require Group administration and independent source sharing authority. Creating an Agent never grants device access automatically.

Execution lists authorize the actual owning Group. Reading does not join; stopping or starting execution requires a current Group write role, an executable Thread and explicit participation. Crew callbacks verify both the exact dispatch's private Runtime owner and the original initiator's current Group, Thread, resource and assignment-generation authority. Neither identity substitutes for the other. A trusted persisted dispatch may bind its own execution session without joining its Runtime owner or granting Group access; ordinary private Task association retains its original owner-access checks. Changing crews, assigning the same crew again, revoking a source or leaving the Thread prevents the old dispatch from publishing new assignments or starting execution. Cancellation settlement of the original private session remains available.

Creation, assignment, comment execution, queue consumption, continuation and actual runtime startup independently recheck the current Group, participation, exact classification, original resource authorization and private definition visibility. Resource authority uses locking current reads rather than reviving revoked permissions from a repeatable-read snapshot. Revocation retains the cancellation protocol: deny new dispatch and claims, and require Runtime confirmation for already running work. CP-01 through CP-20 remain unchanged. Service tests cover source selection and refusal; real cloud, database concurrency and desktop execution require their own evidence.

Project aggregation ordering has an explicit scope independent of the Thread's owning group. Moves still require current owning-group write authority. Project ordering additionally requires current Project Developer authority, actual classification, and a readable anchor under the same parent. Only private Project metadata `board_item_order` changes; foreign-group content, versions, owners and group order remain unchanged. The existing update transaction commits or rolls back the state change and Project order together. Ordinary group ordering retains its original contract. Authorized Project snapshots overlay ranks only for readable items. `test_project_board_order.py`, Native storage transaction tests and the existing desktop board-sorting checkpoint cover denial, persistence and reload without changing CP invariants.

The primary Rust Socket message entry dispatches by explicit container type; the marker grants no authority. Group sends lock the group root, current direct grants, accounts in numeric order and exact Thread before checking current write capability and participation. Messages, ongoing reminders, stand-in wakeups and content revisions commit together; completed Threads retain discussion. Message retries must match the original group and Thread. Post-commit reminder delivery rechecks current membership, participation and mute choices; group links address groups or Threads directly. Real cloud checkpoint acceptance is in progress; compilation or unit tests do not replace it.

Thread statuses are fixed by the actual group container type to `inbox/pending/in_progress/in_review/completed`. Group preferences cannot redefine statuses or their processing boundary, and valid free-text tags require no prior registry entry. Python validation/history, Native work-container projections and Rust preference writes/reads use the shared five statuses. Project aggregation adds those statuses while retaining complete legacy/external columns and unknown historical values without rewriting stored status. Filtering may include history; Thread status mutations accept only shared statuses and still check owning-group authority.

Cloud group creation atomically allocates a unique `groups/{id}` file namespace. Reads, signed URLs, copies and deletes validate stored object keys against the owning container. Moving and recursive deletion validate every source before the first storage operation. Missing namespaces and ambiguous old records are rejected without guessing, moving or removing objects that may belong to another group. `test_group_file_namespace.py` covers same-path isolation and unsafe-record rejection; cloud acceptance checks actual group creation and object contents.

Tools validate dispatched binding scope before choosing a source from the actual stored node. Private local groups need not appear in the project catalog. Backend mirrors retain backend routing; deleted private groups, invalid source metadata and storage errors terminate instead of triggering a backend attempt. Comment reads still validate the Thread's actual owning container. The read-only parent exception continues to require a direct relationship in the same container and current access. Assignment candidates resolve their work container; shared execution separately follows the resource-source and independent authorization rules above.

Historical participation uses only the persisted creator, current human assignee and actual discussion authors in the original container, intersected with active accounts and current target-group grants. Project rosters, reads and Agent ownership are not participation facts. Human chat authors must use canonical valid user ID strings; abnormal values such as `0007` are not aliases for user `7`. Repeated initialization preserves leaving and mute choices without restoring revoked grants. `test_thread_participation.py` covers exact authors, invalid identities and original-container boundaries; helper verification does not establish complete migration acceptance.

Local participants use device identity `0`. Leaving, rejoining and inviting the owner back preserve durable notification preferences and other metadata; only an explicit preference change unmutes. A deterministic participant key with a conflicting type, parent Thread or user is rejected. Archived groups retain readable participation without posting or Thread navigation. Local-store tests cover these boundaries, and the desktop scenario exercises muted leave/rejoin through the UI.

Unsent Thread creation drafts belong to the actor, not the shared group. Cloud drafts are isolated by backend and account across group boards, project creation and the home launcher; local groups use the device's local identity. Rejoining retains mute preferences, and only an explicit notification change replaces them while preserving other participation metadata. Rust group membership management and participant invitations prelock the actor and all target accounts in numeric order before formal authorization, which still validates current roles, active accounts and exact group grants. Identity comparisons use canonical bytes and reject aliases such as `07`. `group_management_locks_shared_accounts_in_message_order` covers real SQL lock waits, mixed collations, canonical identity rejection and actual participation-preference writes; it is not complete cross-runtime HTTP acceptance.

All group writes lock the owning group first; private conversation reservations cannot hold a Thread while waiting for its group. Messages and assignments with comments lock current direct group grants, then every canonically granted group account in numeric user order. They validate the active actor before locking the exact Thread and applying current role, participation and notification gates. Locking all currently granted accounts, including observers and muted members, before participation ranges prevents repeatable-read gap locks from cycling with another group's assignment-index insertion. It does not join or notify members, or look up unrelated accounts. Public comments use the same message path. Other content writes lock and refresh the Thread after group authorization. Agent activity startup and comment execution reuse the Thread execution gate: completed Threads cannot create misleading running activity, while discussion remains available. The existing CI database suite includes `thread_binding_mysql.py` for discussion/reservation and revocation ordering; `thread_current_facts_mysql.py` for deleted-Thread message/delivery rejection, recipient revocation and newly joined/unmuted/approved recipients; and `thread_cross_group_mentions_mysql.py` for explicit mentions, replies to muted stand-ins and actual assignment-with-comment handlers at observed account-lock waits under both isolation levels. Mute suppresses human reminders while preserving a joined stand-in's existing wakeup authority. These concurrency tests establish message and authorization ordering; personal execution has separate execution-scenario acceptance.

Creating a Thread from a project requires an explicit editable owning group. The Thread, initial participants and optional project link commit together. An outer lock on a derived role-precedence query is insufficient: repeatable-read can retain pre-revocation facts. The write transaction locks and refreshes the active actor, project root, parent-space relationship, active space, and direct and inherited grants before applying existing CP05 precedence. Project membership updates share the project-root lock; Rust classification changes lock old and target project IDs in sorted order. `thread_classification_mysql.py` uses real membership services for 16 concurrent cases covering direct/inherited removal/downgrade, both isolation levels and both commit orders. Revocation-first leaves no Thread, link or sequence change. Rust's `thread_classification_reads_current_permission_facts` verifies the current-permission SQL matrix sequentially, not Rust HTTP concurrency. Project PATCH remains Python-routed; this change does not migrate its ownership.

Private task-binding reads authorize the Thread’s actual owning group with current active-account and membership checks, without interpreting a group ID as a project. Members may read their own bindings before joining; this grants no execution authority. Results remain filtered to the caller’s private-task ownership, so other group members cannot read those bindings.

Project aggregation boards may return the current user's own execution previews for group Threads while bindings remain group-owned. Binding queries reuse current group grants for readable linked Threads, restrict results to this read's visible items, and always filter `task_user_id` to the current user. Revoking group access removes both the Thread and its bindings even if project management remains. `test_project_thread_aggregation.py` covers two executors receiving only their own bindings on group and project boards, and group revocation while retaining project authority.

Project boards aggregate existing project tasks and optionally classified group Threads. GitHub/GitLab projects retain their external task sources and add readable group Threads. Reads require an active account, a current direct group grant, and undeleted group, Thread and link records; each projection uses the owning group role. A project administrator cannot read another group through classification, and a project Viewer retains their separate group role. Responses preserve the owning group's `cloud_project_id/group_id`. Reading does not join the Thread or grant discussion or execution, and aggregation does not broaden access to private runtime bindings. `test_project_thread_aggregation.py` covers local and external task sources; local-store tests verify that classification, leaving and unlinking preserve Thread ownership.

Group Thread chat and public comments share one durable message stream; public comments do not create a second discussion record. Chat publication, Thread invalidation and human notifications share a transaction-scoped after-commit queue. Successful savepoints merge into their parent, while partial rollback discards only local events. Publication reads committed state and current authority through a fresh session only after the root commit releases its connection. Rollback and closing an uncommitted session publish nothing; repeated Thread changes coalesce by object. Single-connection tests cover once-only events/notifications, rollback and preservation of outer records after an inner failure.

Message links identify the owning group and storage source, independent of optional project classification. Anchor and page-cursor reads reuse current membership, exact conversation and undeleted-message predicates, including the same NULL/empty legacy root-scope filter. History mode returns only a bounded requested window and never catches up from an old anchor to the latest message in one response. Earlier/later reads are explicit pages; returning to latest restores live following. Reading and pagination never create Thread participation. `test_group_chat_navigation.py` and the desktop group scenario cover old-message access, repeated focus and observer/completed state; these do not replace cloud multi-user end-to-end acceptance.

Thread messages and public comments create ongoing notifications in their original write transaction for current active group members who have joined and have not muted the Thread, excluding the sender. Mentions bypass neither participation nor mute preferences and do not wake an unjoined member's stand-in. A joined member's human notification preference does not change existing stand-in execution authority. Completing a Thread preserves discussion subscriptions. Delayed delivery rechecks membership, exact Thread scope and notification preferences. Muting or leaving stops subsequent reminders while preserving readable notification history. Removing group membership, disabling the account or deleting the group or Thread excludes inaccessible group content from inbox lists, unread counts and read responses. Notifications grant no project or private-resource authority, and legacy project behavior is unchanged. `test_thread_notifications.py` covers both discussion entry points, subscription choices, delayed delivery, idempotency, the read endpoint and recovery. Rust group-notification MySQL coverage reuses the existing coordination-transaction CI suite.

Group realtime reading uses current group membership without requiring Thread participation. Group publication reuses the personal Runtime room joined during authenticated admission. Ordinary messages, cross-process publication and Runtime deltas/snapshots still select recipients from persisted container type, exact Thread ownership and current active group grants; group messages never use a public group room. All online sessions may receive readable group content, which clients filter by group and Thread; transport neither creates ongoing notifications nor joins a Thread. Rust group history subscriptions return bounded windows, and unsubscribe never leaves the personal room, avoiding a history-read versus temporary-room-join gap. Subsequent audience queries exclude removed members and inactive accounts, and lookup failures never fall back to public broadcasts. A delivery already selected before revocation may remain in flight; this mechanism is not an atomic barrier between revocation commit and network delivery. Legacy projects retain their existing message rooms. `test_group_chat_audience.py` covers independent database sessions observing committed revocation and real persisted Runtime projections excluding a removed member from the next packet. Socket.IO and Redis transport boundaries use test doubles; this is not real two-device or independent-process end-to-end verification.

Group writes lock and reread the group root, active account and direct membership grant in the transaction, sharing the group-root lock with membership changes. Archived groups are read-only. Draft delivery uploads, discard and finalization require current write authority and Thread participation before writing object storage. Completed Threads allow discussion but require reopening before execution. `test_thread_participation.py` covers unchanged persistence and storage after rejection. `thread_group_permissions_mysql.py` reuses the existing Issue-assignment CI schema and observes actual MySQL lock waits for both commit orders between comment writes and member removal, downgrade, leaving and archiving. Independent chat groups have distinct resource identities and admission paths; project CP01–CP20 invariants are unchanged. Group membership provides Thread discovery and reading. Discussion, attachment or delivery submission, and execution additionally require current role capability, explicit Thread participation and existing private-resource authority. Historical participation consumes only persisted creator, current assignee and discussion-author facts from the original container, intersected with active accounts and current target-group membership. It never copies a project roster or creates group grants. Ordinary legacy comments cannot distinguish manual input from API publication; use their recorded authors and never infer participants from system, assignment or agent owners. An exact human-answer acknowledgement may arrive after execution completion. The existing Rust Socket.IO projection transaction requires matching device ownership, persisted answer, execution, project, Issue and completed Runtime turn. It locks Issue, execution and activity in that order, then publishes the Issue change after commit without repeating completion notifications. Manual cloud startup retains the durable dispatch queue so transient failures and Executor restarts cannot lose accepted requests. Explicit manual delegation and persistent conversations are independent of automatic intake. Role enablement, project subscriptions, tags, the current assignee and historical assignments or mentions do not gate starting, continuing, retrying or publishing replies. ## Roles and inheritance

The three administrative roles are administrator (`Maintainer`), member (`Developer`) and read-only member (`Viewer`). Ownership is a separate space relation. The read-only `Owner` response label is derived from that relation and cannot be assigned through membership APIs. Creating a project explicitly adds its creator as a project administrator; creator identity is audit information.

The new project, parent-space grant and creator's administrator grant are written in one transaction. Insert the new project's parent grant directly instead of locking an absent grant, avoiding MySQL gap-lock deadlocks when independent spaces create projects concurrently. Resource grants use an atomic insert or update by their unique resource/entity identity before locking the existing record, preserving the grant ID, approval history and outer transaction boundary. The MySQL permission regression suite covers concurrent project creation, concurrent authorization of distinct and identical resources, the unique parent and use permission after creation.

| Space identity   | Inherited project | Restricted project         |
| ---------------- | ----------------- | -------------------------- |
| Owner            | Administrator     | Administrator              |
| Administrator    | Administrator     | Administrator              |
| Member           | Member            | Direct invitation required |
| Read-only member | Read-only member  | Direct invitation required |
| Project guest    | Direct grant      | Direct grant               |

Space owners and administrators always administer child projects. For other users, a valid direct project role takes precedence over inherited space membership, allowing promotion or demotion within that project. Removing the direct grant restores current inheritance. Updating only a member's project responsibilities neither creates a role override nor approves pending or rejected grants. Public reading does not make visitors eligible project participants.

## Protected contracts

Local participation discovery uses a composition-verified scope: native owner `0` and the current verified account principal. This is not a global user alias and grants no cloud authority. Quick filters, pending work, the read-only native pending hint and the local inbox share this scope. Empty idle workbenches add no inbox polling; failed hints remain unknown. New comments use the composition's actual current author without rewriting historical senders. Reply claims still require exact `recipient == persisted comment.sender`: recipient `0` with author `7` requires an explicit transfer, not an alias-based claim. Existing group, read and task-start permissions retain their authorization identity rather than being overwritten by storage owner `0`; CP01–CP20 remain unchanged.

Question reports and blocking updates require both an actual caller-owned active/default Device and the source activity's persisted execution ID, exact project, Issue, Runtime task/device and canonical `executor_owner_user_id`. An owned Device with the same name does not prove ownership of someone else's Runtime. Manual-only bindings or group Runtime activities without matching canonical execution evidence return 409 rather than guessing an owner or deriving identity from a conversation name. Question IDs use the persisted source device identity so changing an alias cannot create another question.

The reporting source may explicitly `set_blocking` only with current Issue Developer access and matching persisted reporter, original Runtime task and caller-owned original device identity. ## Incident and recovery evidence

Development startup automatically runs Alembic. The original permission migration was automatically applied while under development and failed serializing backup data. MySQL retained completed DDL while rolling back project-parent backfill. Startup swallowed the failure, and queries against the empty new parent column hid projects. The earlier claim that no real database had been migrated was inaccurate.

Read-only inspection confirmed all 49 original projects and 49 parent relationships remained, including 29 active projects. No project deletion occurred. The new migration has been withdrawn, original relationship queries restored, and Alembic head is `f3a7c9e1b2d4`. Two unused columns and an empty backup table left by the interrupted attempt are deliberately retained and ignored. Recovery performed no further DDL, bulk data rewrite or role rewrite. Any later cleanup is a separate database operation.

Real development HTTP checks returned 200 with 27 authorized projects and two spaces for admin. Python and gateway WebSocket authentication and project subscription both succeeded. The UI now resubscribes after an initial connection failure and clears the error on success, with cleanup on unmount and Issue changes.

Development startup now aborts on migration failure instead of serving an incomplete schema.
