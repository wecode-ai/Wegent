# Desktop E2E checkpoint and timing review

The fixed baseline `d13154ab65` contains **254 non-group checkpoint registrations** (251 JSON declarations and three dynamically registered release checkpoints). Each was reviewed for timing, duplicate assertions and functional importance. **77 registrations (30.31%) are removed** and 177 retained. This includes ordinary UI matrices, duplicate scenarios, hosted aliases and dead registrations. Complete flows were not regrouped to manufacture deletion counts. Required safety assertions remain in existing hosts; retained coverage is not a claim that every removed UI combination is equivalent.

The inventory initially missed JSON registrations, then missed the three release-suite registrations `app-rollback`, `app-rollback-recovery` and `app-upgrade-recovery`. The complete fixed baseline is 254 and the deletion target is now 77; all three release gates remain. Five later main additions—`connection-observation-storage`, `issue-reference-open`, `paste-image-send`, `runtime-load-performance` and `task-completion-notifications`—are outside that denominator. The current complete catalog contains 182 non-group registrations (179 JSON declarations and three dynamic release entries). Main added immediate-send coverage to `clipboard-history-image`, so it remains outside the deletion count.

## Parallel capacity

[PR #4767](https://github.com/wecode-ai/Wegent/pull/4767) merged as `6841963d00`. Linux Core, Windows Core and Linux Cloud use `CORE_RUNNER_SCALE=1.5`, expanding complete logical selections from 10, 10 and 8 runners to 15, 15 and 12. The per-runner worker limit remains four. Benchmark isolation, exclusive resources and shared preparation groups remain intact; partial selections scale only their assignable work.

## Timing evidence and limits

- Baseline scheduling weights come from the same revision's [Linux table](https://github.com/wecode-ai/Wegent/blob/d13154ab65/.github/ci/wework-linux-checkpoint-durations.json) and [Windows table](https://github.com/wecode-ai/Wegent/blob/d13154ab65/.github/ci/wework-windows-checkpoint-durations.json). Linux Core uses conservative successful-sample statistics; Windows retains per-entry historical measurements and sources. These are not fresh measurements of this change.
- Recent observations use only completed, successful checkpoints from [run 44283945561](https://github.com/wecode-ai/Wegent/actions/runs/44283945561). The overall run was cancelled, so it does not establish a green complete suite. Multiple successful values are shown as a range.
- `—` means no successful timing evidence, not zero cost or a statement about current platform selection.
- `stand-in-startup-recovery`, `project-sidebar-chat`, `goal-resume-route`, `collaboration-local-status-automation`, `responses-api-gateway` and `connector-account-switch` are hosted aliases or dead registrations with no independent CI runtime saving. The deletion ratio describes registrations, not elapsed time.
- Adding historical durations does not measure a new wall-clock speedup. Queuing, setup and resource contention require separate observation.

The nominal 290-second cache difference, three-second uninstall padding and 18-second assignment-window reduction are timing arithmetic, not measured end-to-end savings.

Remaining multi-second timers were reviewed by purpose: cross-second failed-duration labels, real MCP cancellation, memory stability sampling, negative late-event observation, SDK telemetry batching, browser cursor fading and native screenshot/scroll settling retain their contracts. Periodic plugin reconciliation deliberately verifies the real 90–108-second interval. Long-poll and failure guards, and exit waits that complete early, are not unconditional sleeps. The unverified smaller window-fixture experiment was discarded; the original 30-turn/20-page data remains.
