# 项目协作策略 v2

本文件是 W-0063 的协作策略事实源，对应 D029、D033、D036、D037、D039–D047。项目维护者在项目设置中发布可读策略；每次发布生成不可变版本和与上一版本的差异。用户只编辑策略文本，不配置节点、依赖图或执行画布。

## 生效范围

策略用于项目新建和显式应用策略的 Issue。新 Issue 先进入收集箱；发布策略本身不代表批准需求进入本期工作。Issue 创建或显式应用策略时保存唯一实例标识、策略版本、文本和角色快照，准入后才开始六阶段。已有快照不随项目策略更新而改变。

升级运行中 Issue 必须由有权限的人显式执行，填写原因，并记录操作人、新旧版本、保留的历史和迁移影响。已发布的证据、决策和失败记录不可被升级覆盖。无法安全迁移的状态应返回明确原因，等待人工处理。

## 收集箱准入

新 Issue 的状态为 `inbox`，不带六阶段标签，不创建阶段任务，不派发默认助理，也不开始六阶段耗时统计。收集箱允许持续补充描述、附件、关联需求和依赖。

离开收集箱前，有权限的人需要确认以下信息完整，并决定本期是否接纳：

- 目标：为什么做，希望获得什么结果。
- 范围与非目标：本期要交付的内容和明确排除的内容。
- 验收标准：可以通过证据判断的完成条件。
- 依赖：已列明前置事项，或明确确认没有依赖。
- 优先级和拟负责人：完成优先级判断，并选择当前项目中可承担工作的成员。

缺少任何条件时保持收集箱状态，服务端返回缺失条件。准入成功后才进入“需求提出”阶段，并记录准入人、依据、时间和 PMO 通知。

## 六阶段与进入条件

| 阶段 | 参与和负责关系 | 完成及下一阶段进入所需证据 |
| --- | --- | --- |
| 需求提出 | 产品负责需求定义 | 目标、范围、非目标和验收标准 |
| 共同评审 | 产品牵头，研发、UI、测试共同参与 | 研发、UI、测试各自至少一名有效成员对当前 Issue/策略版本提交无异议；评审结论、风险、排期和责任人 |
| 开发准备 | UI、研发、测试、产品共同准备 | 设计稿、技术方案、测试方案或用例、未决问题关闭记录 |
| 开发实现 | 研发负责实现，其他角色澄清和走查 | 合法 PR、可测试版本、自测与联调结果 |
| 质量验收 | 测试验证，产品业务验收，UI 视觉验收，研发修复 | 测试报告、业务和视觉验收结论、问题闭环或授权接受的遗留风险 |
| 发布上线 | 有发布权限的人确认并执行 | 全部必要 PR 已合并；发布授权、成功发布版本、线上验证、回滚准备和复盘结论 |

上一阶段产出满足进入条件后才开放下一阶段。质量验收不能只由测试角色独立兜底。质量验收内部按 QA → 产品 → UI 转交；问题缺陷由研发修复，设计或准备不足回到开发准备，阶段和失败证据保留。合并、发布、高风险操作、冲突证据和低置信度判断必须等待有权限的人确认。阶段批准不等于取得 Git 合并、部署或其他外部操作的执行授权。

## 状态与阶段

Issue 状态表示执行活跃度，协作阶段由策略实例单独保存。服务端始终拒绝或原子修正以下非法组合：

| 状态 | 允许阶段 |
| --- | --- |
| `inbox` | 收集箱，不设置六阶段标签 |
| `pending` | 需求提出、共同评审、开发准备 |
| `in_progress` | 开发实现、质量验收、发布上线 |
| `in_review` | 开发实现、质量验收、发布上线 |
| `completed` | 发布上线，且存在包含全部必要合并提交的成功发布版本 |

从开发准备进入开发实现时，状态在同一事务至少变为 `in_progress`。`in_progress` 不能停留在更早阶段；出现该组合时，服务端提升阶段到开发实现或拒绝写入。状态和阶段的一次修正必须记录原值、新值、来源、时间和操作人，并通知 PMO。

## 负责人与共同评审

需求提出阶段的唯一负责人是产品角色。负责人改为其他用户、智能体或协作组时，服务端在同一事务至少推进到共同评审，或者拒绝改派。

共同评审提交 `StageReviewDecision`，至少包含 `stage_id`、`function_role`、`reviewer_id`、`decision`、`comment`、`evidence_refs`、`issue_version`、`strategy_version`、`created_at` 和 `idempotency_key`。`decision` 为 `no_objection`、`objection` 或 `conditional`。研发、UI、测试各至少一条有效的 `no_objection` 后才允许产品推进；缺失、反对或条件性同意都保持共同评审并返回缺失角色。版本不一致的结论失效，重复提交不得重复推进或通知。

质量验收中，QA、产品和 UI 的 `no_objection` 依次把当前负责人交给下一角色；问题结论保持质量验收阶段、标记阻塞并派给对应修复负责人。

## PR 下限与质量门禁

Issue 正文、评论或活动消息中索引到合法 PR URL 时，Issue 同时获得开发实现阶段下限和 `in_progress` 状态下限。任一维度落后时在同一事务补齐，记录 PR、原值与新值；PR 来源以后被删除也不回退已经发生的状态或阶段。索引 PR 不自动进入质量验收。

进入质量验收要求所有必要 PR 满足：

- 非 Draft；
- 当前 head 的必需 checks 全部成功；
- `mergeable=MERGEABLE`；
- 每个 Issue 都有同一 PR 的明确范围映射、head SHA 和验收证据。

checks 失败、取消、超时或错误时，即使 PR 可合并也不能进入质量验收。尚未进入质量验收时保持或回到 `in_progress` + 开发实现；已进入质量验收时保持质量验收、标记 `quality_blocked` 并切回工程负责人。冲突或 `DIRTY` 执行同样交接，阶段已在质量验收时不回退。重复事件必须幂等，不能重复改派或通知。

全部必要 PR 合并后，研发与 QA 视为完成并进入 `in_review` + 发布上线，清除 QA 待办；未完成的产品或 UI 验收转为发布前检查项。只有存在成功发布版本、该版本包含全部必要 merge commit，并保存版本、URL、时间、目标环境和逐 Issue 映射后，Issue 才能标记 `completed`。

## AI 协调器

协调器读取 Issue 的策略快照、当前版本、当前阶段、可访问的评论、PR、交付物、项目角色以及触发事件。输出必须包含策略版本、Issue 版本、当前阶段、下一负责人、下一动作、满足与缺失条件、可验证的证据引用、必要的人工澄清/高风险确认请求和唯一幂等键。

AI 判断是带依据的建议。服务端负责身份权限、状态与阶段一致性、阶段进入条件、共同评审、PR 门禁、必填证据、幂等、审计和跨用户隔离；不得依据模型声明的“已授权”“已完成”放宽门禁。无法确定、证据冲突或权限不足时进入人工澄清，保留当前阶段。

内部可以生成执行计划，并复用现有工作流定义、Issue 实例、Delivery 和任务结果结构。产品配置和 Issue 主时间线只展示人能理解的阶段、结论与下一步，不展示内部图结构。

## PMO 通知和时间线

Issue 离开收集箱，以及阶段或状态开始、进入等待、阻塞、完成、回退和原子修复时，使用结构化提及通知 PMO。通知和 Issue 时间线摘要至少包含当前状态与阶段、负责人、阻塞项、下一动作、所需证据及决策理由。

通知接收人必须具有当前 Issue 的读取权限。通知失败或接收人不可用必须有可诊断状态，不能以纯文本 `@名字` 冒充已通知。重复提交和重复事件不能产生重复通知、派发或决策。

共享时间线只保留回执、阶段结论、证据摘要和待确认事项；私人讨论、详细工具调用和长过程留在有权限的执行工作间。生成来源、发布来源和确认状态沿用共享时间线的可信度契约。

## 依赖和回滚

项目默认助理花名册、成员授权、派发与持久化回执由 W-0056 提供。本项通过其 ProjectChatAgent 和 Issue assignment contract 路由阶段负责人，不创建另一套派发系统。异步 child conversation、并发请求和 Git worktree 生命周期由 W-0070 提供，本项只保留兼容边界，不作为验收前提。

关闭 `collab.agenticStrategy.v1` 后，新 Issue 回到手工阶段。已发布策略、Issue 快照、证据和审计保留，运行中 Issue 可以按原快照完成；不得通过回滚绕过既有门禁。

## 观测

记录跳步、缺证据批准、阶段变化未通知 PMO、AI 决策无版本或证据引用、状态阶段不一致、PR 门禁绕过、重复通知/改派、成功发布证据缺失等异常。记录策略发布至首个 Issue 采用的时延，以及每阶段 AI 执行、人工处理、等待和退回时长；没有实际执行开始事件时，不推测执行时长。
